# ADR 0018: Deep-link / cast contract + validate-before-navigate resolution

**Status:** Accepted
**Date:** 2026-06-20

**related-files**: source/replayRoute.bs, components/JRScene.bs, components/ItemDetails.bs, source/main.bs, docs/dev/deep-linking.md

The deep-link **wire format** rides entirely inside Roku's ECP `contentId`, pipe-delimited (Roku's own documented convention): a bare item id, OR `id=<id>|serverId=<guid>|action=<verb>` (a bare leading segment is also accepted as the id, so `<id>|action=play` works without `id=`). `action ∈ {open, play, shuffle, trailer}`, defaulting to `open`; an unknown action degrades to `open`, so the contract is forward-compatible — a new verb is additive and harmless on older builds. The route/intent **decides** behavior (play vs open) — it is *never* inferred from the resolved item — and `serverId` resolves only to a server already saved on the device. `contentId` is the whole contract because it is the only field that survives BOTH ingress paths: cold-start `/launch` standardizes only `contentId` + `mediaType` (extra top-level params are dropped), while runtime `/input` forwards arbitrary params. Roku also forbids `&` inside `contentId` and reserves the top-level `action` key, so nesting under `contentId` with pipes is the only encoding that is portable across both paths and collision-free. Rejected: **top-level ECP params** (dropped on cold-start; a top-level `action` collides with Roku's reserved launch key); a **router-path-shaped `contentId`** (welds the external contract to volatile internal route strings the #550 migration churned repeatedly); and **inferring play-vs-open from the resolved item's type** (the sender's intent must be explicit, so a deep link can't silently start playback).

The **resolution model** validates the id — a metadata fetch, behind a non-blocking spinner — *before* any navigation (`JRScene.resolveDeepLink`). An invalid id (or a failed fetch) therefore never disturbs the active session: it shows a toast and nothing else — no navigation, nothing torn down — so an unauthenticated LAN `curl` of junk ids is harmless, and only a valid id navigates onward. Post-login the app lands on Home first and then validates, so an invalid id just toasts on Home. The one exception is a **cross-server** link, which can't be validated until after its user-confirmed server switch (we aren't authenticated to the target server beforehand), so an invalid id there toasts post-switch. This replaced an earlier *navigate-then-validate-then-bail* approach in which `ItemDetails` was the validator: it navigated to a doomed details screen and then tried to `goBack`, which raced the router's coalescing `routerState` and stranded the user on a blank/stale screen ~50% of the time. Validating first removes the race by construction — the deep-link path never navigates to a screen it has to immediately unwind. This contract is the shared spine of the "Cast to JellyRock" epic (#669): the same `parseDeepLinkContentId` format is consumed by the ECP deep-link path now and minted by the future remote-control "play" path (#666/#667), which reuses the same `stashDeepLink` / `onRuntimeDeepLink` launch seam.
