# ADR 0045: A live stream's open is handed off by stage, and waits as long as the server can

**Status:** Accepted
**Date:** 2026-09-26

**related-files**: `source/utils/liveStreamHandoff.bs`, `source/enums/LiveStreamStage.bs`, `source/enums/AbandonedLoadAction.bs`, `components/ItemGrid/LoadVideoContentTask.bs`, `components/ItemGrid/LoadVideoContentTask.xml`, `components/video/VideoPlayerView.bs`, `source/api/items.bs`, `source/api/apiResponse.bs`, `source/constants/timeouts.bs`, `tests/source/unit/platform/TaskStopProgress.spec.bs`, `tests/source/unit/utils/liveStreamHandoff.spec.bs`, `docs/architecture/playback.md`, `docs/architecture/threading.md`

`LoadVideoContentTask` opens a Live TV live stream in `PlaybackInfo` (`AutoOpenLiveStream`), and the server opens it whether or not the app is still waiting (`OpenLiveStream(request, CancellationToken.None)`, 10.7.7 through 12.1); only the answer names the stream. Two ways of leaving that answer unread left the stream, and on a tuner-limited server a tuner, open until the server restarted, on every version: Back pressed while `PlaybackInfo` was in flight, because `VideoPlayerView.onDestroy` STOPped the load (reproduced 2026-09-26 on a Stick 4K against 10.7.7, 10.10.7, 10.11.11 and 12.1.0 with the answer held 6 s), and an open slower than the default 10 s HTTP limit, which also showed a generic error for a channel that would have played (a source answering at 12 s, 10.7.7 through 12.1.0). Now the load records its stage on its own node (`liveStream`: `opening` before `PlaybackInfo`, `open` with the id after it; the view marks `handedOver` or `released`), writes `open` before it reads `isAbandoned`, and `VideoPlayerView.releaseVideoLoad` decides from the stage: stop a load that has opened nothing (as before, so it sends nothing and changes no queue), close then stop a load that holds a stream, and let a load whose stream is `opening` finish that one request, marked abandoned, so it closes the stream and ends. A live open asks for `timeouts.LIVE_OPEN_MS`, 120 s: the server gives up on a source that never answers after its own 100 s and answered a source that responded at 95 s after 98.5–99.5 s including its first-open probe, so every open the server can complete is heard (measured 2026-09-26, 10.7.7, 10.11.11, 12.1.0). At the limit the viewer sees "This channel took too long to start" (`apiResponse.noAnswer`). Verified on a Stick 4K against 10.10.7, 10.11.11 and 12.1.0: Back while opening, Back at the instant of the answer, a 15 s open that now plays, and the regular end paths each released the stream exactly once, and Back took effect in about 0.3 s with the answer held 20 s, from a details screen and from a deep link.

**It rests on a measured platform property:** a stopped Task makes no further node access, whether it was mid-way through ordinary code or its `wait()` had just been answered (0 further writes in 40 of 40 trials on a Stick 4K and on a 512 MB Stick, OS 15.3.4; a read after the STOP did not return either). So after the view stops a load that holds a stream, the load can neither close it again nor send anything, and exactly one side closes whichever order the two land in. `TaskStopProgress.spec.bs` gates it in every unit run. **Ruled out:** letting the whole load finish after Back (it would run the queue changes that precede `PlaybackInfo`, such as appending a series' next episodes, into whatever the viewer plays next); cooperative checkpoints throughout the load (a load-specific mechanism against [ADR 0037](0037-task-run-replacement.md)'s stop-the-run rule, and every future step would need its own check); releasing the stream in the API pool when an answer arrives for a caller that has gone (the pool's liveness check and the view's STOP can interleave, leaving a stream nobody closes, unless the pool gains a render-thread handoff); and no limit on the open, as jellyfin-web has. A source that answers but never sends data keeps the server waiting with no limit and never yields a stream id, so "no limit" would hold a pool slot and a thread forever per attempt, and a few attempts would stop the whole app talking to the server. That server-side wait is not the client's to fix and is not reported upstream.
