# ADR 0022: HTTPS "Cast to JellyRock" — companion-plugin HTTP long-poll transport

**Status:** Accepted
**Date:** 2026-07-13

**related-files**: `source/remotecontrol/remoteProtocol.bs`, `components/remotecontrol/RemoteControlTask.bs`, `source/remotecontrol/remoteCommand.bs`, `source/api/baseRequest.bs`, `source/utils/deviceCapabilities.bs`, `docs/architecture/remote-control.md`, `docs/architecture/remote-control-longpoll-contract.md`

This is the **HTTPS half** of the two-transport "Cast to JellyRock" vision ADR 0021 set up; the `ws://` half (#666) stays as-is. Roku has **no socket TLS** (no `wss://`), so a secure server can't push over the session `WebSocket`. Instead a **companion Jellyfin server plugin** ("JellyRock Companion", repo `jellyfin-plugin-jellyrock`) attaches an `ISessionController` that **queues** the `Play` / `Playstate` / `GeneralCommand` frames the server fans out, and JellyRock **pulls** them with an authenticated HTTP **long-poll** over TLS (`roUrlTransfer`), reusing the existing `remoteCommand.parseMessage` → `dispatchCommand` → `remoteDispatch` pipeline unchanged. The wire contract is **frozen + versioned** (`contractVersion` 1) as a published doc (`remote-control-longpoll-contract.md`) so a future client — e.g. the official Roku app, which shares the no socket TLS limit — can adopt it without plugin rework. Verified end-to-end on real hardware (Jellyfin 10.11.11): a web-cast `Play` reaches JellyRock and starts playback over `https`.

**Three load-bearing decisions, all verified on device.** (1) **One `RemoteControlTask` branches internally on server scheme** (`http://` → `ws://`; `https://` → probe the plugin's `/info`, then long-poll) rather than a second Task node — the plugin-presence probe is Task-thread I/O, so keeping transport selection where the I/O already lives avoids any main-thread probe step; `main.bs`, `globals.bs`, `Home.bs`, `userAuth.bs`, and `deviceCapabilities.bs` are all **unchanged**. (2) **The plugin owns the `SupportsMediaControl` capability on `https`** — JellyRock keeps advertising it `false` (`deviceCapabilities.bs` stays scheme-gated); the plugin forces it `true` while a poll is live. (3) **Closed-app liveness rides the plugin controller's poll-freshness, not `LastActivityDate`.** Jellyfin's `SessionInfo.SupportsRemoteControl` (what the web cast list filters on) is a live computed getter — the capability flag **and** a controller reporting `SupportsMediaControl` — recomputed on every `/Sessions` query. So a controller whose `SupportsMediaControl` reads `false` once no poll arrived within a grace window drops JellyRock from the cast list with **no background sweep** and no `OnSessionControllerDisconnected` (which doesn't exist in the 10.11.11 interface). On device, `SupportsRemoteControl` flipped `true → false` within ~24s (50s grace) of the app closing **even though `LastActivityDate` stayed warm** from other traffic — which is precisely why liveness can't ride `LastActivityDate` / `activeWithinSeconds`. Rejected: `wss://` on Roku (impossible — no socket TLS); a **second Task node** (duplicated lifecycle wiring across `globals`/`main`/`Home`/`SignOut`, no concurrency benefit since transports are mutually exclusive per session); **JellyRock advertising the capability on `https`** (chicken-and-egg with the async probe at the synchronous capabilities-POST site, and the plugin must revoke on close regardless); **`LastActivityDate`-based liveness** (kept warm by unrelated traffic, proven insufficient on device).
