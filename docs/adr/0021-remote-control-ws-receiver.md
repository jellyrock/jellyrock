# ADR 0021: Native "Cast to JellyRock" — `ws://` remote-control receiver (Option-B threading)

**Status:** Accepted
**Date:** 2026-07-09

**related-files**: `source/remotecontrol/remoteCommand.bs`, `source/remotecontrol/remoteProtocol.bs`, `source/remotecontrol/remoteDispatch.bs`, `components/remotecontrol/RemoteControlTask.bs`, `components/remotecontrol/RemoteControlTask.xml`, `components/vendor/BrightWebSocket/WebSocketClient.xml`, `source/utils/deviceCapabilities.bs`, `source/main.bs`, `source/utils/globals.bs`, `source/api/userAuth.bs`, `docs/architecture/remote-control.md`

JellyRock becomes a first-class Jellyfin cast target ("Play On") via **two transports feeding one normalized command stream**; the **`ws://` half ships now (#666)**. Jellyfin pushes remote-control commands (`Play` / `Playstate` / `GeneralCommand`) to a session over a **`WebSocket`** only — there is no ECP/SSDP/DLNA path, and with no open socket the command is silently dropped server-side. Against a plain-**HTTP** server, JellyRock opens Jellyfin's native `/socket` directly, with **zero server changes**. The secure/HTTPS future is a **server-plugin HTTP long-poll** (#667), **not `wss://`**: Roku has no socket TLS (`ifSocketOption` exposes none; the vendored `BrightWebSocket` fork and every maintained variant are `ws://`-only), so `wss://` is impossible on the platform. Because of that, the receiver **only** opens a socket when the server base URL is `http://` — it never downgrades an `https://` session's token onto cleartext `ws://`; the advertised capability and the receiver gate on the same predicate so they can't disagree. Rejected: `wss://` on Roku (not achievable — no socket TLS); an ECP/SSDP cast (Jellyfin has zero awareness of it); a core-server change (fights the DLNA removal direction and needs maintainer buy-in — the plugin is opt-in and needs neither).

**Threading = Option B.** The socket is I/O, so it lives on a **Task thread** (`RemoteControlTask`, which owns the vendored `WebSocketClient` node — the proven nested-task precedent); the seams a command must drive (`stashDeepLink` / `onRuntimeDeepLink`, `getActiveView`, `roAppManager`, `m.scene.callFunc`) are **main-thread** only. So the Task **only** parses + normalizes each frame (the pure `remoteCommand.parseMessage`) and marshals a command to the main thread, where `main.bs` dispatches it via `remoteDispatch` (sharing `Main()`'s `m`, like `replayRoute`). The marshalling field rides on the **task node** (`dispatchCommand`), **not** `m.global`, because an `m.global` field observed by the main loop's port does **not** deliver (the delivery defect noted in `main.bs`); a task-node field + port does. `remoteDispatch.dispatchTransport` is **shared** with the voice path — `main.bs`'s `roInputEvent` branch was refactored to call the same adapter — so voice and cast dispatch transport identically. Rejected: dispatching on the Task thread (the deep-link/player/`roAppManager` seams can't run there); marshalling via an `m.global` field (doesn't deliver to the main loop).

**Two constraints are load-bearing.** (1) **Capabilities:** `SupportsMediaControl` is what makes the session appear in "Play On" *and* what carries **transport** control (pause/seek/next/…); `SupportedCommands` (`getSupportedRemoteCommands()`) must contain **only `GeneralCommandType` values** (`["DisplayContent"]`) — putting any `Playstate` verb (Pause/Stop/Seek/…) there makes the whole `POST /Sessions/Capabilities/Full` return **400**, so *nothing* sticks and the device never registers. Transport rides on `SupportsMediaControl`, never on `SupportedCommands`. (2) **Scope = single item now.** A `Play` casts `itemIds[startIndex]` — one item — through the deep-link seam (`contentId` `<id>|action=<verb>`), reusing ADR 0018's validate-before-navigate contract. The full `ItemIds` list / `StartIndex` / `StartPositionTicks` are parsed but not consumed; **multi-item queue casting** (`PlayNext`/`PlayLast`, start-position) is a deferred followup. Casting an episode still yields a navigable queue because the *player* builds its own next-episode queue; casting an album currently plays only the first track. This receiver is the `ws://` half of the "Cast to JellyRock" epic (#669); it mints the same `parseDeepLinkContentId` format ADR 0018 defined.
