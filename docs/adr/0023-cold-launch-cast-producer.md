# ADR 0023: Cold-launch cast producer — phantom session, device-validation gate, `net9`/10.11 floor

**Status:** Accepted
**Date:** 2026-07-17

**related-files**: `source/replayRoute.bs`, `source/main.bs`, `source/remotecontrol/remoteProtocol.bs`, `components/remotecontrol/RemoteControlTask.bs`, `docs/architecture/remote-control.md`, `docs/adr/0018-deep-link-cast-contract.md`, `docs/adr/0022-remote-control-https-longpoll.md`, (`jellyfin-plugin-jellyrock` repo) `Jellyfin.Plugin.JellyRock/RemoteControl/PhantomSessionService.cs`, `Jellyfin.Plugin.JellyRock/RemoteControl/PhantomSessionController.cs`, `Jellyfin.Plugin.JellyRock/RemoteControl/PairingDecision.cs`, `Jellyfin.Plugin.JellyRock/RemoteControl/PairingValidationService.cs`, `Jellyfin.Plugin.JellyRock/RemoteControl/RemoteControlController.cs`, `Jellyfin.Plugin.JellyRock/Jellyfin.Plugin.JellyRock.csproj`, `Jellyfin.Plugin.JellyRock/build.yaml`

This is the **producer half** (#668) of "Cast to JellyRock" — the closed→open bridge that makes a *closed* JellyRock appear as a "Play On" target and cold-wakes it into content. It completes the epic whose receiver half ADR 0021 (`ws://`) + ADR 0022 (`https` long-poll) built: those carry commands to an **open** app; this ADR advertises and wakes a **closed** one, then hands off to that live channel. The producer lives entirely in the companion plugin (`jellyfin-plugin-jellyrock`) plus a small client-side pairing report; it mints **no new wire format** — the wake reuses the ECP deep-link `contentId` contract frozen in ADR 0018 verbatim (`id=<id>|serverId=<guid>|action=<verb>`), so the same seam the receiver already consumes (`stashDeepLink` → `replayAfterLogin`) is what the cold launch lands on. Scope is strictly the closed→open bridge: once the woken app opens its live #666/#667 session, control is the receiver's; the producer stops advertising and never carries a transport command.

**The phantom session — one continuous identity, open XOR closed.** A closed JellyRock is advertised by a **phantom** `SessionInfo` that a sibling `IHostedService` (`PhantomSessionService`, 30s timer — *not* an extension of `JellyRockSessionService`) publishes for each paired device that is advertisable **and** reachable **and** not currently open. The phantom is minted via `ISessionManager.LogSessionActivity` keyed on the **paired real `DeviceId`**, so it resolves to the *same* `SessionInfo` the live app uses when open — the open/closed transition is which controller reports liveness, **not** a session swap. That identity continuity holds **only when the app presents one stable `DeviceId` across every channel**. On the **HTTPS** path it does: both `RemoteControlController.Pair` and `.Poll` derive the device identity from the same `Jellyfin-DeviceId` **auth claim** (never a body field), so one sign-in's token yields one `DeviceId` for the pairing and the live long-poll. The **HTTP path does not, by default** — the native `ws://` session keys on the client's `serverDeviceName` (not the auth claim), and `serverDeviceName` (`device.id + username`) was *unstable across startup* (bare `device.id` before login, suffixed after), splitting one physical device into **two** sessions: the phantom on the `/pair` `DeviceId`, the live `ws://` socket on the other. This ADR's on-device E2E surfaced that real client bug; it is resolved by decision [`deviceid-suffix-gate-10.11`](../decisions.md) — a stable bare `device.id` on 10.11+ so every channel agrees. **Cold-launch on HTTP depends on that fix.** While closed the phantom advertises a **reduced** capability set (`SupportsMediaControl=true` to stay in the picker; `SupportedCommands=[DisplayContent]` so jellyfin-web renders only the wake affordance, no no-op transport controls — the lever validated in the `P0` spike and inherited from ADR 0022's capability-state model). Selecting it fires ECP `POST /launch/<appId>?contentId=…` from `PhantomSessionController`, reading the freshest `WakeIp`/`AppId` from config at fire time. The open/closed swap needs **no controller detach and no session swap**: the phantom controller **self-suppresses** its ECP wake whenever the app is open, and the service **skips publishing** then — so both the "don't double-fire the wake" and "don't stomp the open app's real caps" concerns are correct-by-construction across the transition, in both directions. "Open" is detected **transport-agnostically** (`PhantomSessionService.IsAppOpen`): *any live non-phantom controller* on the session — the long-poll `QueueingSessionController` on HTTPS **or** Jellyfin's native `ws://` `WebSocketController` on HTTP (both report `IsSessionActive` from their live transport). The earlier long-poll-only check read a wide-open HTTP app as closed; the transport-agnostic form (the same shape Jellyfin's own `SessionManager` uses for liveness) is what makes the swap correct on HTTP too. Reaper-safe by the same construction: `ReapDecision.IsReapable` gates on `hasNowPlaying`, and a phantom has none.

**The device-validation gate — self-enforcing, no special cases.** A Roku is advertised only if the server can *actually reach it over ECP on the LAN*. JellyRock reports its wake address on receiver start — `POST /JellyRock/RemoteControl/pair {rokuIps: GetIPAddrs(), appId, isDev}` — and `PairingValidationService` probes those IPs over the **ungated** ECP `GET /query/device-info` (needs neither dev mode nor "Control by mobile apps"). Reachable → a validated scalar `WakeIp` is persisted; unreachable → the record **never validates**, so `PairingDecision.ShouldPublish` (`IsAdvertisable && !appIsOpen && reachableNow`, pure/unit-tested) never advertises it. This makes the Charter's hard limitation *self-enforcing* rather than special-cased: a remote/cloud server, a reverse-proxied session onto a friend's own Roku, an ECP-disabled or powered-dark device — none validate, so none are advertised, with no "is this LAN-local?" heuristic to get wrong. Liveness is **service-driven** (`SetLive` per tick from pairing-validity **plus a live reachability re-probe**), deliberately **not** poll-freshness (a *closed* app never polls, so poll-freshness — ADR 0022's open-app liveness signal — would mark every closed device dead) and **not** unconditional (the spike's shortcut, which would keep advertising a powered-off Roku). A device that goes dark therefore revokes within one tick. Reachability + freshness(14d) reaping are **internal constants, not user config** — self-correcting and invisible, so a knob would be config bloat; promote only on evidence.

**`net9` / Jellyfin 10.11 compile floor (absorbs decision `companion-net9-floor`).** The phantom must name the `User` entity (`LogSessionActivity(User)` + `IUserManager.GetUserById`), which moved to `Jellyfin.Database.Implementations` in the 10.11 DB refactor — a 10.9-floor build throws `TypeLoadException` the instant the phantom `JIT-compiles` on 10.11. `jprm` ships **one `DLL` per manifest entry** and Jellyfin does **no** target-framework probing, so a single assembly cannot both carry the phantom and load on 10.9/10.10 — cold-cast is 10.11-only under *every* option. We **floor-bump the whole companion `net8`/10.9 → `net9`/10.11** rather than ship a two-track `net8;net9` release: existing 10.9/10.10 servers stay on the last 10.9-`ABI` release (gated by the manifest `targetAbi`) and simply stop being offered newer versions. Chosen for simplicity given a young plugin (v0.2.0) whose install base skews to current-stable 10.11; the plugin's deliberate 10.9 compile-floor is the evidence weighed against it. Proven by execution — the `net9`/10.11 build loads and runs on a real 10.11.11 server with no `TypeLoadException`.

**The 3rd-party-ECP policy caveat (adopted with eyes open).** Roku's docs discourage *3rd-party* platforms from sending ECP to Roku devices ([external-control-api.md:47–53](https://github.com/rokudev/dev-doc/blob/v2.0/docs/DEVELOPER/dev-tools/external-control-api.md)). We adopt it anyway because the tradeoff is favorable and bounded: the sender is the user's *own* LAN-local Jellyfin server (not a cloud relay), the surface is a single `/launch` wake reusing our own documented deep-link contract, and there is a clean fallback if Roku ever tightens ECP — a plugin-side device picker (worse UX, but the feature degrades rather than breaks). The validation gate already confines ECP to devices the server can reach on its own LAN, which is exactly the LAN-local posture the policy is least hostile to.

**Rejected.** A **rival/extended service** owning both open and closed caps (the `P0` "extend `JellyRockSessionService`" sketch) — the sibling `PhantomSessionService` + shared `SessionInfo` keeps open-app ownership untouched and makes the swap self-suppressing rather than coordinated through one class; the two services coordinate via the shared session, not a merged lifecycle. **A synthetic phantom `DeviceId`** — would make open/closed two identities and reintroduce the double-presence failure the auth-claim keying rules out. **Poll-freshness liveness for the phantom** — a closed app never polls (see above). **`/launch`-always (skip the open/closed split)** — when the app is open the live #666/#667 channel already carries commands, and `/launch` to a foreground app re-inits disruptively; routing on "have a live session?" costs no new state. **A cloud/LAN-relay agent** for remote servers — cut entirely; ECP can't reach a Roku whose server isn't LAN-local, and the validation gate makes that a self-enforced limitation, not a bug. **A two-track `net8;net9` release** and **a reflection-based phantom in a single `net8` build** — both deferred/ruled out under `companion-net9-floor` above (release-pipeline surgery vs. fragility on exactly the version-sensitive surface that changed).

**Auth-deferral on cold wake is inherited, not new.** A cold ECP `/launch` is an ordinary Roku cold-start whose `contentId` lands in `launchArgs`; `main.bs` stashes it (`stashDeepLink`) *before* the login flow and `replayAfterLogin()` replays it — immediately if a token exists, else once sign-in completes — so a Roku woken **signed-out** stashes the intent and opens it after login with no producer-side work. The producer therefore relies on the existing receiver/deep-link machinery (ADR 0018) for the post-wake half and adds nothing to it.
