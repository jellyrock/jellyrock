# ADR 0041: A Task launch past the thread watermark waits in a queue instead of being refused

**Status:** Accepted
**Date:** 2026-09-23

**related-files**: `source/utils/tasks.bs`, `tests/source/unit/utils/tasks.spec.bs`, `tests/source/unit/platform/TaskRelaunch.spec.bs`, `tests/source/unit/utils/tasksLaunchQueue.spec.bs`, `components/tasks/TaskLaunchQueue.bs`, `components/tasks/TaskLaunchQueue.xml`, `components/testing/TaskLedgerBench.bs`, `source/utils/globals.bs`, `components/video/PlayerHostView.bs`, `docs/architecture/threading.md`

[ADR 0031](0031-task-thread-ceiling.md) made `launchTask()` refuse above `TASK_THREAD_WATERMARK` (50) live threads and return `false`. Only `HomeRows`' section loads check that return. An audit on 2026-09-23 found that most of the other ~45 app launch sites set something before launching that only the run's delivery undoes: a loading spinner, a pending screen-load fill, an in-flight flag (`TrickplayCarousel.m.taskRunning`, `m.isLoadingFavorites`, `m.isLoadingLatestRows`), a record button's `isLoading`, or `JRButtons`, which shows no buttons until its task delivers. A refused launch leaves each of these stuck for the life of the screen. Now, above the watermark, `launchTask()` queues the node, returns `true`, and starts it when a slot frees. No call site has to handle a refusal, and a saturated app shows content late rather than never.

**Considered and ruled out.** *Undo at each site, plus a build rule that every `launchTask()` result is used.* Correct, but 30+ undo paths that only run with the app at 50 threads, so none can realistically be tested, and every future site must write one. *Remove the refusal and let `&h29` crash.* Visible in Roku's crash reports, which is how #728 was found, but crashing is what the ceiling exists to prevent. *Keep the refusal.* Leaves the stuck states in place. The queue follows the usual shape of a bounded worker pool: queue work while the workers are busy, and reject only when the queue itself is full.

**The design, and the evidence behind each rule.**

- **The drain is a render-thread `Timer` that runs only while something is queued.** Roku signals a thread's end only through the node's `state` field. Having the queue observe `state` on running nodes would risk removing another component's observer on the same field when it unobserves (#898 showed an `unobserveField` in one component can do that; `TrickplayCarousel` observes its own loader's `state`). It would also reintroduce the per-launch observer PR #765 removed. Draining only on the next `launchTask()` call would strand queued work in a quiet app. Every `launchTask()` caller is on the render or main thread (grep, 2026-09-23), so a render-thread drain can start any queued node. Two measurements on a 512 MB Streaming Stick `3600X`, Roku OS 15.3.4, 2026-09-23, shape how it is scheduled. **Setting `control = "start"` on a running `Timer` restarts its countdown:** starting the drain Timer on every queued launch kept a waiting launch from starting until the launches stopped (launches 50 ms apart, a free slot: it started 85–90 ms after the last one, 3 of 3). So the Timer is one-shot, started only when the queue goes from empty to waiting, and re-armed by each tick that leaves something waiting. **A retry that finds no free slot costs render-thread time:** 2.8 ms each at the watermark when it asked `admitTaskLaunch`, which writes the ledger twice; 2.1 ms reading the ledger only (`TaskLedgerBench` `drainBlocked`). A blocked tick therefore only reads it, and retries back off while none can start, doubling from 100 ms to at most 400 ms and resetting once one starts. That bounds a saturated app's retry cost to about 5 ms of render-thread time per second, where a fixed 100 ms retry spent about 28, and it matters beyond the frame budget because a busy render thread also slows the Tasks the queue is waiting on ([async.md](../architecture/async.md#crossing-the-thread-boundary-costs-a-rendezvous--budget-crossings-not-bytes)). The cap is how late a waiting launch can notice a freed slot; 400 ms was chosen over 800 ms for latency, since both cost well under a frame per retry.
- **A node STOPped while queued is dropped, not started.** Measured on a 512 MB Streaming Stick `3600X`, Roku OS 15.3.4, 2026-09-23: a STOP on a node that has never run sets `state = "stop"`, and a later RUN still starts it. So each queue entry records the node's `state` when it was queued, and the drain skips any entry whose state has moved since. That covers `releaseTask()`, `replaceTask()` and a raw STOP alike, for every node that had not run before. **The gap:** a persistent node relaunched after a finished run is queued reading `"stop"`, and a STOP while it waits leaves it reading `"stop"`, so that release cannot be seen and the run starts late. The sites that relaunch one node after a finished run are the `PENDING_MIGRATIONS` entries in `no-same-node-relaunch` (`VideoPlayerView`'s `LoadMetaDataTask`, `AudioPlayerView`'s, two in `ItemDetails`, `Home`'s remote-control receiver), plus two the plugin does not list: `TrickplayCarousel.m.tileLoader`, which waits for `state = "stop"` before relaunching, and `VideoPlayerView.m.liveTvRefreshTask`. At those sites a release while waiting cannot be seen. For the trickplay loader the worst case is a tile download that finishes with nobody listening. Migrating a site to a new node per run ([ADR 0037](0037-task-run-replacement.md)) closes the gap for it. An audit of every launch site found none that drops a node without STOPping it first. `TrickplayCarousel`'s teardown looked like one, but its `reset()` STOPs the loader just before.
- **A node is queued at most once.** Sites that still relaunch the same node (`PENDING_MIGRATIONS` in `no-same-node-relaunch`, `TrickplayCarousel`, live-TV refresh) call `launchTask()` on a node that may already be queued. Relaunching a node that is already queued keeps its place in the queue and re-records its state, so a release followed by a relaunch while it waits still starts it once. The run reads its latest inputs when it starts. Relaunching a node whose thread is running is ignored, exactly as Roku ignores it today.
- **A queued node is in flight.** `isTaskInFlight(node)` answers "launched or queued, and not finished". `PlayerHostView`'s poll tick uses it in place of `state = "run"`. Otherwise it would replace its own queued fetch every tick and send it to the back of the queue.
- **Queued nodes are not counted as live threads**, so the queue never blocks its own drain. The count stays derived from `state`, per ADR 0031.
- **The queue is capped; past the cap, `launchTask()` refuses as it does today.** Measured on the `3600X` above: a never-launched `LoadItemsTask` holding small inputs costs 3.6–4.1 KB (1,000 nodes +3.52 MB, 2,000 +7.48 MB, against a 300 MB channel limit). A cap of 500 bounds the queue to about 2 MB on the smallest supported device, so one fixed cap is enough and no per-device cap is needed. Only a runaway fan-out can reach it, and then refusing is the backstop, as in ADR 0031.
- **A late start is allowed.** If a queued Record, Play or Shuffle starts after the user has moved on, it still runs, because they asked for it. Screens that should cancel on leave STOP their node at teardown, which the drain honors.

**What this does not change.** `launchTask()` still returns `false` for an invalid node. The watermark (50) and the release-time `task-thread-peak` gate (30) stay the same, and that gate remains the primary defense ADR 0031 describes. A store build still has no channel to report saturation, so queuing makes a fan-out slower rather than broken, and no more visible. Under `#if perfTiming`, the existing `taskLedgerRefusals` / `taskLedgerFirstRefused` trace gains a queued-launch count and a peak queue depth. Caller-side timeouts can still re-queue a waiting run at the back: `HomeRows` releases a run after 20 s of silence. That only bites while the app stays saturated for longer than the timeout.

**Tests.** `tasksLaunchQueue.spec.bs` drives the pure queue rules directly (dedupe, skip-if-stopped, cap, the room check at the watermark and its agreement with `admitTaskLaunch`, the retry schedule), and runs the real `launchTask()` against a real `TaskLaunchQueue` on device: a queued launch starts once a slot frees, a STOP while queued is skipped, waiting launches start in order and a new one cannot jump them, the drain keeps running while new launches arrive faster than one retry, a launch that waited through the backoff starts within the longest retry of a slot freeing, and a full queue refuses. Rooibos does not run on the render thread, so one case launches through `TaskRelaunchProbeHost`, which calls `launchTask()` there, as the app does.
