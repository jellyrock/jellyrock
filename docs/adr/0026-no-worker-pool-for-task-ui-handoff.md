# ADR 0026: No worker-pool tier for Task→UI handoffs; the render thread is the shared bottleneck

**Status:** Accepted
**Date:** 2026-08-09

**related-files**: components/home/LoadLatestRowsTask.bs, components/home/HomeRows.bs, source/api/apiPipeline.bs, docs/architecture/async.md

Epic #728's Phase 1 named an orchestration job pool (K workers + FIFO coordinator, children-as-vehicle) as the mechanism for Home's `emit`-bound orchestrator. **It is rejected, by measurement rather than argument, and will not be built.** Splitting Home's `emit` a level below the existing wait/emit instrumentation (Streaming Stick 4K, 11 rows, n=10, `debug=false`, and reproducing session 6's independently-recorded 1342 ms at 1350) showed only **224 ms of a 2695 ms run** is thread-local work K workers could divide — the transform plus a carrier node. The other ~1100 ms is the Task thread *parked inside a render-thread observer callback*. Projected K=3 payoff was **−6%**, against three extra threads, a new orchestration primitive, and a deadlock class to design out. Re-open only on a fresh measurement showing `xform` is the dominant column, never on argument.

The governing mechanism, proven with a dose-response rather than a single contrast: **writing a Task-node field that the render thread observes parks the writing thread for the duration of the observer's callback.** Three writes in one build, one campaign, differing only in what observed them, cost 0.8 ms/row (unobserved), 1.8 ms/row (observed, empty callback) and **40.1 ms/row** (observed, callback sleeping a known 40 ms) — slope 1.00, intercept ≈ 1 ms. This matches Roku's documented rendezvous semantics (`rokudev/dev-doc` v2.0, `DEVELOPER/core-concepts/threads.md`): *"the response appears synchronous to the invoking thread"*, and *"all observer callbacks on the fields are executed in the Render thread."* The architectural consequence is the line in that same document — **only the render thread may serve a rendezvous** — which makes it a shared serialization point for every cross-thread operation in the app. Task-side parallelism cannot relieve a bottleneck that all Task-side work must queue against.

Ruled out: **(a) build the pool anyway** for the bounded-by-construction story — unnecessary, since `launchTask()` plus the `no-raw-run` BSC plugin already deliver the thread bound; the pool was only ever the *perf* half of Phase 1. **(b) Decouple the write so the two threads overlap** — this was built and measured, not reasoned about, and it is the more valuable half of this record because it is the idea a future reader will reach for first. Making the observer schedule a render-thread Timer instead of draining inline moved `notify` 1092 → 258 ms exactly as predicted, and `wait` (+633 ms) and `append` (+351 ms) absorbed all of it: `total` went 2695 → 2733 ms, U = 0.0 against a null expectation of exactly 50, **p = 0.97**. A busy render thread merely relocates the queue into the other rendezvous. Note [`async.md`](../architecture/async.md#crossing-the-thread-boundary-costs-a-rendezvous--budget-crossings-not-bytes) already warned of this ("expect a busy render thread to slow the Task down, not just the other way round") — read it before prototyping any handoff change.

What shipped instead attacks the render thread's own work rather than the Task thread's: batching the per-item attach (`row.appendChildren` in place of a 16-iteration `appendChild` loop) cut Home first paint **2646 → 2129 ms**, complete separation across arms (U = 0.0, p = 0.0002, n = 10 each), verified against the live node counts so a render-less-work result could not pass as a win. The repeatable form of that lever, and the discriminator that decides where it applies — the target must already be in the live render tree — is tracked as [`per-item-cross-thread-appends`](../architecture/tech-debt.md#per-item-cross-thread-appends). That entry also records why the *mechanism* behind the cost is deliberately left unnamed.
