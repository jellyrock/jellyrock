# ADR 0044: A loading spinner is started by the kind of wait it covers

**Status:** Accepted
**Date:** 2026-09-25

**related-files**: `source/enums/LoadingKind.bs`, `source/utils/loadingStages.bs`, `source/utils/screenWaits.bs`, `source/utils/misc.bs`, `components/JRGroup.xml`, `components/JRScene.bs`, `components/JRScene.xml`, `components/search/SearchResults.bs`, `docs/architecture/navigation.md`, `components/CLAUDE.md`

The scene's one spinner covers waits that are not alike, so a wait is now named by its kind, and the scene applies that kind's rules for what the viewer is told and what Back does. Four kinds are defined in [navigation.md → What kind of wait a spinner is](../architecture/navigation.md#what-kind-of-wait-a-spinner-is): **content load** (a screen waiting on the server for its own data: Back leaves, and the pool skips a read nobody is waiting for), **playback start** (the server opening a play session: Back leaves at once, the request is allowed to finish, and whatever it opened is closed when the answer lands — stopping the request does not stop the server opening a live stream, measured 2026-09-21 when a client that gave up left the stream held 11 min), **buffering** (the player's own), and **session change** (sign in or out, switching user or server: blocked on purpose). Kinds whose wait is a server answer say so under the spinner on its own line — "Still loading…" from 8 s, "The server is taking a while to answer." from 30 s (`loadingStages`) — and no other kind gets stage text, so the text is never false and a caller's own text above the spinner is never replaced.

**A screen's waits live on the screen, by name.** A screen opens and ends each wait it has — `screenWaits.begin(m.top, "results")` / `screenWaits.finish(m.top, "results")`, kept in its `loadingWaits` field — and the scene shows the waits of the active routed view only, the way it already projects that view's overhang fields. So the spinner follows the screen rather than the last call anyone made: it goes when the screen closes, hides while another screen is on top, and comes back when the screen returns, still counting from when each wait began; a screen can end only its own waits; and it stays up until the last of several ends. Measured wrong on a Stick 4K before this (2026-09-25): Back mid-search left the spinner, and its stage text, over Home; a search answer landing after the viewer opened a result stopped the details screen's spinner ~9 s in, with its data still loading; and returning to a search still loading showed no spinner. A survey of every spinner start the same day found the cause is general: every stop ends whatever spinner is up, several screens can have two waits at once (details: its metadata and a cast; the grid: its first page and the TV guide), and waits are handed across navigation on purpose (details or the grid start one that the player stops). The scene's own spinner (`startLoadingSpinner()`, a cast) shows over a screen's waits, which show again when it stops. Built first: screen waits, used by `SearchResults`; the cast resolve is the scene's own content load, canceled by Back. Waits the whole app is in — playback start, session change — are the next step: named app waits, ended by name, each with a time limit that ends and logs one nobody ended. `startLoadingSpinner()` stays the plain spinner, today's behavior, for any call site not yet moved, so a site moves only when it meets its kind's rules.

**Considered and ruled out.** *One spinner with one wording for every wait* — waits that are not server answers (mid-playback buffering, an audio scrub, the LAN server scan, sign-out teardown) would be told something false, and callers with their own spinner text (a live channel's name, the fallback-font download) would have it overwritten. *Neutral wording for all kinds* keeps it true but drops the server hint where it is accurate. *A stage timer per view*, as PR #1043 adds to the library grid — a second copy was about to be written for Live TV. *An ownership flag per screen, stopped in `onDestroy`* (#1043's `m.ownsSpinner`) fixes only a screen closing, and every screen has to remember it. *The scene recording which screen started the spinner and the base screen releasing it* still loses a wait on return, and a nested panel such as the TV guide is not the routed screen. *One boolean or a counter per screen* cannot hold two waits, and a counter drifts on a missed or doubled end. *Callbacks the spinner calls when a wait is done* run the dependency backwards and can call a screen already destroyed — the hazard `abandonApiPromises()` exists for. **Limits:** the stages reach the viewer only for a wait allowed to run long. A screen whose wait is one request on the default limit gives up at `timeouts.API_WAIT_MS`, so it shows "Still loading…" only briefly and never the 30 s stage; search makes four requests in sequence, so a slow search can reach it. A wait's age is read from the wall clock (`loadingStages.nowMs()`), which a time sync can step, showing one stage early or late. **Revisit if** a wait fits none of the four kinds.
