# ADR 0044: A loading spinner is started by the kind of wait it covers

**Status:** Accepted
**Date:** 2026-09-25

**related-files**: `source/enums/LoadingKind.bs`, `source/utils/loadingStages.bs`, `source/utils/misc.bs`, `components/JRScene.bs`, `components/JRScene.xml`, `components/search/SearchResults.bs`, `docs/architecture/navigation.md`, `components/CLAUDE.md`

The scene's one spinner covers waits that are not alike, so a call site now starts it by the kind of wait it is, and the scene applies that kind's rules for what the viewer is told and what Back does. Four kinds are defined in [navigation.md → What kind of wait a spinner is](../architecture/navigation.md#what-kind-of-wait-a-spinner-is): **content load** (a screen waiting on the server for its own data: Back leaves, and the pool skips a read nobody is waiting for), **playback start** (the server opening a play session: Back leaves at once, the request is allowed to finish, and whatever it opened is closed when the answer lands — stopping the request does not stop the server opening a live stream, measured 2026-09-21 when a client that gave up left the stream held 11 min), **buffering** (the player's own), and **session change** (sign in or out, switching user or server: blocked on purpose). Kinds whose wait is a server answer say so under the spinner on its own line — "Still loading…" from 8 s, "The server is taking a while to answer." from 30 s (`loadingStages`) — and no other kind gets stage text, so the text is never false and a caller's own text above the spinner is never replaced. `startLoadingSpinner()` stays the plain spinner, today's behavior, for any call site not yet given a kind, so a site moves only when it meets its kind's rules. Built first: `LoadingKind` with `PLAIN` and `CONTENT`, and `startContentLoading()`, used by `SearchResults.searchMedias` and `JRScene.resolveDeepLink`; each content-load start restarts the clock, because a new query supersedes the last.

**Considered and ruled out.** *One spinner with one wording for every wait.* A survey of every `startLoadingSpinner()` call site on 2026-09-25 found waits that are not server answers (mid-playback buffering, an audio scrub, the LAN server scan, sign-out teardown), where "the server is taking a while" would be false, and callers with their own spinner text (a live channel's name, the fallback-font download) that stage text written into the same label would overwrite. *Neutral wording for all kinds* keeps it true but drops the server hint where it is accurate. *Opt-in stages on the single spinner* — a wait under 8 s shows nothing either way, so opt-in bought nothing; the real problem was truthfulness, which kinds solve. *A stage timer per view*, as PR #1043 adds to the library grid — a second copy was about to be written for Live TV. **Limits:** the stages only reach the viewer for a request allowed to run long; a request on the default limit gives up at `timeouts.API_WAIT_MS`, so its screen shows "Still loading…" only briefly and never the 30 s stage. **Revisit if** a wait fits none of the four kinds.
