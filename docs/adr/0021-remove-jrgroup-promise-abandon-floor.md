# ADR 0021: Remove the `JRGroup`/`JRScreen` promise-abandon floor

**Status:** Accepted
**Date:** 2026-07-04
**Related:** ADR 0013 — `auto-abandon-promises-bsc-plugin` (supersedes its base-class floor)

**related-files**: components/JRScreen.bs, components/JRGroup.bs, scripts/bsc-plugins/auto-abandon-promises.cjs

ADR 0013's base-class floor (`abandonApiPromises()` unconditionally called from `JRGroup.bs`/`JRScreen.bs onDestroy()`, added to cover non-overriding subclasses the plugin's per-file detection can't reach) turned out to have zero live consumers. An audit of every `fetchAsync` call site (`UserSelect.bs`, `VideoPlayerView.bs`, `ItemDetails.bs`, `schedule.bs`, `BaseGridView.bs`) confirms each already defines its own `onDestroy()` (plugin-injected or hand-written), and no shared `source/` helper wraps `fetchAsync` for an indirect caller — the floor's target scenario doesn't exist anywhere in the codebase today. Its cost, though, was universal: because SceneGraph merges ancestor `<script>` scope into every descendant, the floor's `import "pkg:/source/api/apiPromise.bs"` pulled `promises.brs` into the inherited script scope of literally every `JRGroup`/`JRScreen` descendant — nearly every screen and panel in the app — whether or not that screen ever touches a promise.

Investigating GitHub issue #689 (Roku OS 12.5 / Roku Express `4K` install failure, "Error parsing multiple XML components") surfaced this: `components/JRGroup.bs` was the one file confirmed unchanged and present across both a failing `v2.21.0` release and a later failing prod-`main` build, making it the strongest candidate root cause found. `components/JRGroup.bs` is deleted (it existed solely to host the floor); `components/JRScreen.bs` reverts `onDestroy()` to a no-op and drops the `apiPromise.bs` import, matching the state before ADR 0013. The plugin's own direct-call detection + build-time enforcement (unaffected by this change) remains the sole mechanism guaranteeing abandon-on-destroy; a future component reaching `fetchAsync` only through a shared helper is not caught by either the plugin or this floor and must abandon manually — already documented as a known limitation in the plugin's own comments.

**Caveat carried forward, not resolved by this change**: on current `main`, `JRGroup` now extends `sgrouter_View` (the sgRouter navigation migration), and `sgrouter_View.xml` itself unconditionally lists `promises.brs` — plus `router.brs`, `RouterState.brs`, `rodash.brs`, `interfaces.brs`, `bslib.brs` — as a hard dependency of the router library itself. This change removes the path specific to JellyRock's own code, but does not remove `promises.brs` from `JRGroup`'s inherited scope overall. Whether the exposure that sgRouter forces on its own is sufficient to reproduce #689 is untested (no OS 12.5 device available) and unresolved; if it is, decoupling `JRGroup` from `sgrouter_View`'s promise dependency would need its own decision.
