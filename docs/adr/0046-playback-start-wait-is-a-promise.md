# ADR 0046: A playback start's wait is a Promise per start

**Status:** Accepted
**Date:** 2026-09-27
**Partially supersedes:** [ADR 0044](0044-spinner-by-kind-of-wait.md) (app waits end by their Promise, not by name)

**related-files**: `source/utils/appWaits.bs`, `source/enums/LoadingKind.bs`, `source/utils/loadingStages.bs`, `source/constants/timeouts.bs`, `components/AppWaitHost.bs`, `components/JRScene.bs`, `components/JRScreen.xml`, `components/manager/QueueManager.bs`, `components/video/VideoPlayerView.bs`, `components/music/AudioPlayerView.bs`, `components/ItemDetails.bs`, `tests/rta/specs/playback-start.spec.js`, `docs/architecture/navigation.md`

A playback start runs from a press on one screen to a player on another, so its wait cannot live on either screen ([ADR 0044](0044-spinner-by-kind-of-wait.md) named these "app waits" and deferred them). Every start now opens a `PLAYBACK_START` app wait: `QueueManager.beginPlaybackStart()` asks the scene's `AppWaitHost` for a Promise (`appWaits.begin()`, through `callFunc` only), the scene shows the spinner and its 8 s / 30 s stage text until that Promise settles, and the player that mounts takes it (`takePlaybackStart()`), resolving it when its stream loads and failing it on a failed load or in teardown. The first settle wins and later ones do nothing, so every exit path ends it without checking. Leaving the screen the start was pressed on before any player exists fails it (`appWaits.leftBehind()`; a screen that plays declares `JRScreen.isPlaybackScreen`) and stops the Play all / shuffle build, which only reads; a time limit (`timeouts.PLAYBACK_START_LIMIT_MS`, outlasting a live open plus the load's other requests) fails and logs one nobody ended. A start still hides the screen it was pressed on, now by `opacity`, which the router never touches, and while it does, `AppWaitHost` holds the remote focus: the hidden screen takes no keys, Back cancels the start and shows that screen again, and every other key waits for the start to end. Measured on an Ultra against 12.0 with the answer held 8 s (2026-09-26), before this: Back mid-start from a grid left the plain spinner up over the grid and then Home, 35 s and counting, with the scene holding the remote disabled; Back during a Series "Play all" let the player launch on the grid once the episode list arrived. `playback-start.spec.js` gates both.

**Why a Promise and not a name.** ADR 0044 planned app waits ended by name. A name cannot tell two starts apart: the player a channel switch replaces used to need an `isSwitchingChannel` flag so that its own stop did not end the next channel's spinner, and every handover would need a guard like it. With one Promise per start, code holding a start can only settle that start. **Ruled out:** ending by name (above); a plain string token per start (the same identity, but without the promise library's settle-once and `onFinally` delivery, and a second completion vocabulary beside the promises the render thread already uses, [ADR 0012](0012-promise-native-interface-fetchres-exception.md)); keeping the plain spinner and stopping it in the player's teardown (it stops whatever spinner is up, including the next channel's). Screen waits keep ending by name, which is safe there because a screen can only reach its own.

**Why the start holds the focus.** A hidden screen that keeps the focus keeps taking keys nobody can see the effect of. A second OK started a second launch whose navigation the router rejects mid-transition, which fails both starts and leaves the player loading with no spinner (read from the code, not run); arrows moved a focus nobody could see; and Back left the screen Play was pressed on, one step further back than Back from the player, which returns to it. So while a start hides its screen, the focus moves to `AppWaitHost`, a child of `JRScene` outside the router outlet: Back reaches `JRScene`'s Back arbiter, which cancels the start (`AppWaitHost.cancelOnBack`) unless a navigation is in flight (then it is swallowed, as it always was, and the navigation mounts the player), and the host ignores every other key. When no start hides a screen, the active screen takes the focus back through the router's `handleFocus`, restoring what the host saved (`JRScreen.saveLastFocus`). **Ruled out:** keeping the remote live and guarding only the second launch (Back stays inconsistent and the hidden focus still moves); the scene-wide lock `isRemoteDisabled` (it swallows only the keys that reach the scene, and it blocks Back). The host is its own component, not scene code, so a unit test can mount it and reach the whole wait, focus included. The session-change and buffering kinds, and photo launches, stay on the plain spinner until they are moved.
