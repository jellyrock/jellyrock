# ADR 0043: The API pool stops a long read whose caller has gone

**Status:** Accepted
**Date:** 2026-09-25

**related-files**: `source/api/apiTimeout.bs`, `source/api/apiPool.bs`, `components/api/ApiQueueTask.bs`, `components/api/ApiTask.xml`, `source/api/baseRequest.bs`, `source/api/apiPromise.bs`, `source/constants/timeouts.bs`, `components/ItemGrid/LoadItemsTask2.bs`, `tests/source/unit/api/apiPoolStop.spec.bs`, `tests/source/unit/api/apiTimeout.spec.bs`, `tests/rta/specs/slow-library.spec.js`, `docs/architecture/api.md`

A large library on a server whose database has not been optimized answers its first grid page in ~40 s (measured 2026-09-24, Jellyfin 10.11.11, 8,643 movies: 39.9–42 s, first byte at 34.6 s), and every pool request gave up at `timeouts.HTTP_MS` (10 s), so the grid showed "No Items" (#869). A request AA may now carry its own `timeoutMs`; the HTTP call uses it, and every wait on the request derives from it (`apiTimeout.waitMs`: the limit plus the margin between `API_WAIT_MS` and `HTTP_MS`, so the HTTP layer still gives up first), for `fetchRes` and `fetchAsync` alike. A grid page asks for `timeouts.GRID_PAGE_MS` (60 s, the default `proxy_read_timeout` of `nginx`). A minute-long request is only acceptable if backing out gives its pool slot back, so this reverses the part of [ADR 0040](0040-pool-skips-abandoned-reads.md) that ruled out canceling a request already on a slot: when the coordinator sends a read with a longer-than-default limit (`apiRequestIsStoppable`), it subscribes to the waiting Task's `state`, reads it once (a Task that stopped before the subscription sends no event), and when that Task stops before the answer it adds a `quit` field set to true to the slot, removing it again before the slot's next request. `roku-requests` already reads `m.top.quit` on every pass of its wait and cancels the transfer when it is true — through its timeout path, because its quit check reads `m.cancel_and_return` instead of its local variable, which is harmless only while the pool passes no `retryCount`. The subscription is one per Task rather than one per request: `unobserveField` drops every observer of the field, so a Task with several long requests on slots (an `apiPipeline` run) would otherwise lose its watch on the rest when the first is answered. Measured 2026-09-25 on a 512 MB Stick against the slow server: the transfer ended 139 ms after the stop and the slot took the next request at once; the first page loaded in 44 s.

**Only long reads are watched.** Reading the waiting Task and subscribing cost 0.5–1.0 ms each on the coordinator (same device and date), on the serial path every request takes, and a default request frees its slot within 10 s anyway; the decision rides the request AA, so every other request pays nothing. Writes are never stopped, for 0040's reason. **Ruled out:** watching every read (the cost above, per request, for a saving capped at 10 s); the scoped observer pair, which would avoid `unobserveField` dropping every observer of a Task's `state` but needs Roku OS 12 while the app supports 11 — safe today because nothing else observes a Task's `state` (the task ledger reads it by design); and replacing the `roku-requests` wait loop in the same change. That loop polls without sleeping and reads `quit` as a rendezvous on every pass (98.7% of its time, measured 2026-09-25) — it predates this, it touches every request in the app, and it is tracked as its own followup with a before/after measurement. Also ruled out: declaring `quit` on `ApiTask`. `roku-requests` reads it on every pass of every request, and a declared field measured about twice as costly to read as a missing one (2026-09-25, 512 MB Stick, local 10.11 server: 6.9 ms against 3.7 ms median per read, more total wait in 4 of 4 rounds). A render-thread request has no waiting Task to watch, so a long one would not be stopped; none exists, which is why the grid's `/Items/Filters` request keeps the default limit (followup in `docs/progress.md`).
