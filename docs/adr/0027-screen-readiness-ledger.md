# ADR 0027: A screen declares its pending fills; paint and settle fall out of the ledger

**Status:** Accepted
**Date:** 2026-08-13

**related-files**: `source/utils/screenReadiness.bs`, `components/ItemDetails.bs`, `components/extras/ExtrasRowList.bs`, `components/extras/ExtrasRowList.xml`, `scripts/measurements.js`, `scripts/measure.js`, `docs/projects/2026-08-measurement-platform/PLAN.md`

A screen does not become ready at one moment, so no screen may hardcode "its" second milestone. `ItemDetails` paints from one metadata fetch and then keeps filling, and WHICH fills are outstanding depends on the item type: a Series swaps a loading placeholder for its Resume button, a Person swaps one for Shuffle, a Playlist grows a Watched button, a Movie grows a Trailer button, a Season back-fills ratings from its parent series, an Audio item fills lyrics — and all nine types run the extras chain. Between two and four fills are outstanding at paint time. The draft criterion this replaces assumed one number per screen and named the resume button as the second milestone; that is wrong for eight of the nine types, because for a Movie or an Episode the resume button is built SYNCHRONOUSLY inside the content handler from `playbackPositionTicks` already on the node.

So the screen declares each outstanding fill (`pending`/`resolve`) and the two milestones are derived: **paint** when it renders, **settled** when the declared set empties. This is the split the mature platforms publish rather than choose between — the web's first-paint metric against its network-idle one, Android's time-to-initial-display against `reportFullyDrawn()` — and both make the same admission the ledger encodes: the framework can see the first frame, but only the app knows when the content the user came for landed. Measured on `.177`, the split is not academic: `movieDetails` painted in **404 ms** and settled at **3057 ms**, with the ledger naming `extras` (2677 ms) as the slowest fill. A single first-paint number would have flattered that screen by 7.5×. `seriesDetails` painted in 197 ms and settled at 845 ms with a different fill set, which is the generalization check: same family, same lines, no per-type parser.

Because the emit is uniform by construction and the screen names itself in the line, `scripts/measurements.js` gets ONE `screen-load` family covering every instrumented screen present and future — instrumenting the next one is app-side work only. That inverts the registry's "add an entry per screen" note rather than contradicting it: a registry beats a parser because the EXISTING lines disagree about their shape, and a new shape that agrees with itself needs an entry per shape, not per instance. The legacy per-component families stay and answer a different question (where the time went INSIDE one loader); neither is derivable from the other. The screen therefore arrives as a parsed DIMENSION rather than an operator's `--screen` assertion — the same argument that made `enableRta` derived rather than assumed — and the item type rides along as `variant`, which is what makes a sample attributable when a chained navigation mounts one screen more than once per launch.

**Fills carry a class tag rather than being filtered.** A fill is `content` (it changes what the screen says) or `texture` (an image load), decided mechanically by what resolved it rather than by a per-site judgment about whether the user notices — judgment rules drift, mechanical ones do not. Both are recorded; `content` headlines. Excluding texture loads was considered and rejected as the irreversible half of the choice: a noisy texture timing can be ignored later, but a fill never recorded can never be joined to a series taken before it existed — which this project has already paid for once, when `deviceKey` was added to the run ledger after four runs had been taken. `contentMs`/`textureMs` are SUMS OVER CONCURRENT fills and are explicitly not shares of `settledMs`; they can exceed it (a Series settled in 845 ms with `contentMs` 878), so neither may be rendered as a percentage.

**The gate lives inside the module, not at the call sites.** `scripts/harden-prod-manifest.js` forces `perfTiming=false` into every release artifact, so a shipped build compiles the ledger to empty subs — one call and no allocation per fill — and an instrumented screen reads as four plain statements instead of four `#if` blocks. That is what makes adding the next screen cheap enough to actually happen, which is the whole thesis. The one failure that must never be silent is a screen painting with no ledger open (`begin` not called on the path that load took): it warns, because silence there is indistinguishable from a screen that never painted, and diagnosing it once already cost a device round trip while every other signal — the transpiled output, another family's `perfTiming` bracket, the extras chain's own HTTP traffic — said the instrumentation was present and running.

**Rejected.** A **generic spinner clock** in `JRScreen` stopped at `stopLoadingSpinner()` — two edits, every spinner screen measurable — killed on three findings before it was built: `stopLoadingSpinner()` has 38 call sites across 15 files and 10 of them are not screens, so it would emit from flows that never painted; `settings.bs` and `OSD.bs` extend `JRScreen` and never call it at all, so it buys less than it advertises; and the 29 RTA screens collapse to ~8 components, so accurate per-loader instrumentation is only ~6 investigations and the tradeoff it traded against does not exist. (`JRScreen` remains the right home for a DECLARED ledger — every target component extends it — and was only ever the wrong home for an INFERRED clock.) **A universal "time to focusable" metric** — cheap, covers everything, and produces one number that cannot say why. **Two families per screen** (paint and settled measured separately) — the two milestones describe one load, and splitting them makes a change that speeds paint by deferring work into extras invisible in each record. **Stopping the paint clock at the first `renderTracking` callback** — closer to what the eye sees, but it fires repeatedly and needs a per-screen rule for which fire counts, which is the per-screen knowledge the ledger exists to remove. **Deriving chain completion from a counter of in-flight tasks** in `ExtrasRowList` — needs a line at the end of all twenty-odd handlers instead of the four actual tails, each silent when forgotten.
