# ADR 0030: A measurement arm with no ODC asserts its identity by ENCLOSURE, and records that it did

**Status:** Accepted — specified; not yet implemented
**Date:** 2026-08-16

**related-files**: `scripts/measurement-guard.js`, `scripts/measure.js`, `scripts/measure-compare.js`, `tests/scripts/unit/measurement-guard.test.js`

> ⚠️ **Nothing in the tree implements this yet.** The rule below is written in the present tense because it describes the contract the harness must be built to, but no code carries `identitySource` and `measure:compare` does not yet know the sanctioned exception — grep either and you will find nothing, which is the expected state, not a removal. This ADR is step 2 of the three-step ODC calibration tracked in [`docs/progress.md`](../progress.md); building to it is the front half of step 3. Flip this status line to plain `Accepted` when the harness lands. Recorded ahead of the code deliberately: the decision is a *prerequisite* of the harness, so writing it afterwards would mean the harness had already chosen.

The measurement platform's calibration question — *does a resident ODC component move a first-paint number?* — requires an arm with no resident ODC component. That arm is one deploy option away: `device.deploy({ injectTestingFiles: false })` skips both the `ENABLE_RTA=false` → `true` rewrite of the staged manifest and the injection of the on-device component, off the same `build/` directory the paired arm ships. Everything the sampling loop needs survives that: `hardRelaunch()` is pure ECP, and the console reader is a telnet socket on 8085. **Exactly one thing does not survive it — the identity read**, which is ODC and nothing else (`readIdentity`, `scripts/measurement-guard.js`). So the arm that has to exist for the calibration to happen is the one arm that cannot observe what server it measured against, and tier 1 is the gate that a sample nobody can attribute to a server is not a sample.

Three ways out were available and two of them are worse than they look.

**Skipping the assert** — recording `asserted: false` for the non-ODC arm, which the guard already supports and reports loudly — is the cheapest, and it puts the blind spot exactly where the confound lives. The failure tier 1 exists to catch is a device sitting on a server nobody meant to measure, and that failure has the same shape and the same silence in a non-RTA build as in an RTA one: the run completes, the samples are well-formed, only the workload is wrong. An arm that cannot be attributed is not evidence about ODC; it is evidence about an unknown server.

**Carrying the identity across from the paired arm and recording it as identity** is worse, because it is wrong in the way this subsystem is least able to detect. The redeploy between the arms does not touch the registry, so the inference is very probably true — and `readIdentity` throws rather than reporting absent fields precisely so that an unanswered request can never be laundered into a fact. A record that says `serverUrl: <url>` makes a claim about an observation. Writing an inference into that field would make every downstream reader — `checkSeriesConsistency`, `measure:compare`'s mixing gates, a future matrix report — treat a deduction as a measurement, with nothing on the wire to say which it was.

**So the arm asserts by ENCLOSURE.** The harness brackets the non-ODC block with observed ODC reads taken in the adjacent RTA arms, and the block's identity is the identity both brackets agree on. This is a real assertion rather than an inference dressed up, because what it rests on is narrow and checkable rather than probable:

- The app's server and user come from the registry, and `measure.js` never writes the registry — an invariant its own header states as the term any seeding mode must adopt `lib/registry.js` to break.
- The only operations between the two observed reads are `npm run build`, `device.deploy`, ECP `Home` / `launch`, and reading a console socket. None of them writes the app's registry.
- **Both** brackets must agree with the declared `--server` *and* with each other. A disagreement fails the whole enclosed block rather than one arm, because the enclosure cannot say at which point inside it the identity moved — which is the honest consequence of measuring at the boundary instead of at the sample.

What enclosure does **not** claim is that the identity held at each individual sample. That is strictly weaker than the per-session read the RTA arms get, and the record says so by field name rather than in a comment somebody has to find: the provenance carries `identitySource: 'enclosed'` with both bracketing reads beside it, never `'observed'`. A reader that wants only observed identities can filter on one field, and a reader that does not know the distinction exists is told by the value it reads.

**Rejected, and worth recording because it is the obvious fourth option:** having the app print its identity onto the console under `perfTiming`, which would make identity observable in both arms from the same artifact that produced the number — strictly better evidence than either read. Two reasons it is not this ADR's answer. It puts the developer's own server URL into every console scrollback, a surface this project has already had to scrub twice (`#820` replaced a real LAN address with the RFC 5737 documentation range in two files), where the record on disk was already an accepted, single, non-pasted location for it. And it adds an emit to the very instrument the calibration is measuring, so the arm designed to establish the instrument's footprint would ship a larger instrument than the one whose footprint is published. Revisit it if identity ever needs to be observable per SAMPLE rather than per session — the ledger's own `instrumentUs` now makes the second objection quantifiable rather than a matter of judgment.

**Consequence for `measure:compare`.** Its refusal of arms differing in `ENABLE_RTA` is correct and stays the default; the refusal text already names this calibration as the thing that would have to have happened first. The sanctioned exception is explicit rather than a bypass flag: it requires both arms to carry an identity — observed or enclosed — and those identities to agree. An arm with `asserted: false` still cannot be compared, which keeps the cheapest of the three options above from becoming the path of least resistance.
