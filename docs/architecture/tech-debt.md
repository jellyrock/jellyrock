# Tech Debt & Cruft

A living inventory of known issues, plus a "recently removed" list (so future-you doesn't waste time searching for ghosts that have been deleted).

For *what's good and shouldn't be casually reformed* — see the relevant topic doc in [`docs/architecture/`](./README.md#topic-map--load-by-purpose). Each topic doc explains its subsystem's design intent inline, where the context is fresh.

Each refactor item has a stable slug for cross-referencing in commits, PRs, and GitHub issues. When a slug is filed as a GitHub issue, add the issue number as the `github` field. When the work is complete, remove the entry entirely (the closed GitHub issue becomes the historical record).

## How to use this document

- **Considering a refactor?** Check this list first. If the area is here, the change is at least documented; pick severity carefully — `low` items are usually quirks with reasons.
- **Considering a major change to a "clean" subsystem?** Read the relevant topic doc in [`docs/architecture/`](./README.md) first. The clean systems are clean for reasons that aren't always obvious from the code alone, and those reasons live in the topic docs (e.g., the persistent task pool's children-as-vehicle dodge for SceneGraph event coalescing is in [`api.md`](./api.md), the DoVi `buffer:loop:` retry is in [`playback.md`](./playback.md)).
- **Filing a GitHub issue?** Reference the slug in the title and link from the issue back to this entry. Add the issue number to the entry's `github` field here.
- **Fixing an entry?** Remove the entry from this file in the same PR. The git history of this file becomes the audit trail of what got fixed when.

### Citing a slug from another doc / comment

Use the **anchor-link form**, not narrative prose:

```markdown
[`manual-theme-cascade`](../../docs/architecture/tech-debt.md#manual-theme-cascade)
```

In code comments / diagnostic strings (where markdown won't render), use the bare anchor: `tech-debt.md#manual-theme-cascade`.

The `npm run lint:docs` checker validates every `tech-debt.md#<anchor>` reference against the actual headings in this file, so deleting a slug catches stale references at push time. Naked narrative mentions like `` `manual-theme-cascade` `` (no anchor) are not checked — there's no syntactic signal to distinguish them from any other backtick-wrapped kebab-case identifier — so the convention exists to keep the check bulletproof. If you find yourself mentioning a slug, link it.

## Severity rubric

- **High** — meaningful complexity costs; fixing genuinely improves agent + human DX. Worth scheduling.
- **Medium** — worth refactoring when adjacent (touch the area for any reason → fix in passing).
- **Low** — minor irritants, low blast radius. Often quirks with rationale; fix only if the surrounding work makes it cheap.

## Refactor candidates

### High

#### `itemdetails-size`

- **area**: `components/ItemDetails.bs`
- **issue**: Single file handles **16 distinct item types** via per-type `populateInfoGroup<Type>` renderers (Movie, MusicVideo, Episode, Series, BoxSet, Season, Person, MusicArtist, MusicAlbum, Playlist, Audio, Photo, PhotoAlbum, TvChannel, Program, Recording). 3,600+ lines, ~90 top-level functions, 100+ line `onKeyEvent`. Extras pane animation logic (grid + gradient overlay + slide interpolators) interleaved with Task-result handlers; the inline `TrackDropdown` cluster (~20 functions for pre-playback audio/subtitle/source selection) is also embedded here.
- **direction**: Split per item-type renderer (`populateInfoGroupMovie`, `populateInfoGroupSeries`, etc.) into separate modules under `source/details/` or `components/details/`. Extract: (a) the extras pane (animation + grid + gradient overlay) into its own component, (b) the `TrackDropdown` cluster into its own component (already self-contained — wire via fields), (c) the resume button + logo/date-label clusters as smaller helpers. `onKeyEvent` shrinks naturally as each subsystem owns its own focus / key handling.

#### `videoplayerview-size`

- **area**: `components/video/VideoPlayerView.bs`
- **issue**: 2,119 lines, 67 top-level functions, 133-line `onKeyEvent`. Mixes native `Video` event handling, the playback state machine (`onState`), OSD action dispatch, trickplay, transcoding decisions, the DoVi `buffer:loop:` retry flow, subtitle management (~8 fns), chapter navigation (~4 fns), audio/source track switching (~4 fns), next-episode + media-segment notifications (~10 fns — the largest embedded subsystem), Live TV / DVR-recording mode (~8 fns: channel switching, EPG refresh, live-edge math), and Jellyfin reporting.
- **direction**: Extract subsystem controllers, each owning its own observers + key handling: `SubtitleController` (~8 fns), `ChapterController` (~4 fns), `TranscodeRecoveryHandler` (DoVi retry + error dialog + force-finish, ~6 fns), `NotificationController` (next-episode + media segments, ~10 fns), `LiveTvController` (~8 fns — trickiest because it couples tightly with the underlying `Video` state machine; extract last). The player class is left with lifecycle, state-machine observation, OSD dispatch, audio/source switching, trickplay UI sync, and reporting.

#### `mainbs-event-loop-fan-out`

- **area**: `source/main.bs`
- **issue**: 444-line file (down from 1,315 as of #677 — the #550 sgRouter migration removed the search, audio `playItem`, `optionSelected`, and `closeSidePanel` branches plus their inline logic; the dead resume/start-over playback-options flow was deleted in #757). `Main()` spans the whole file: bootstrap (Phase 1 globals → migrations → theme → login → Phase 2 globals) then the main event loop (`roSGScreenEvent` screen-closed, `exit`, `preLoginIntent`, `isAuthenticated` + `close` quick-connect, `isFontDownloadCompleted`, `reachable` server-probe, `userMenuAction`, `roDeviceInfoEvent`, `roInputEvent` deep-link, `isDataReturned` dialog-return, `reloadHomeRequested`). Some heavy work is extracted into `handle*` helpers (font, menu, login); the `isDataReturned` branch still fans out two confirmation-dialog flows (server-switch / exit) inline.
- **direction**: Continue the handler-extraction pattern — the `isDataReturned` branch is the largest remaining inline block and the clearest extraction candidate (`source/handlers/dialogs.bs`). Bootstrap extracts to `source/bootstrap.bs` so `Main()` becomes `bootstrap()` + a thin dispatch loop.

#### `task-thread-budget`

- **area**: `components/**/*Task.*` (26 Task component types), `source/utils/globals.bs`, `source/main.bs`, plus `JRScreen` `onDestroy` teardown across routed screens.
- **github**: #728 (crash manifestation — `&h29` "Too many task threads" on large libraries)
- **issue**: Roku OS caps concurrent Task threads at **50 (soft) / 100 (hard)** per app. JellyRock runs a fixed floor of ~5 persistent API-tier tasks (3× `ApiTask` pool + `ApiQueueTask` coordinator + `SideEffectTask`), plus `RemoteControlTask` (and a nested `WebSocketClient` task on the `ws://` path) and the two font tasks. On top of that floor, transient per-screen tasks (`ItemGrid/LoadItemsTask2`, `tasks/QuickPlayTask`, `ItemGrid/LoadVideoContentTask`, `liveTv/LoadChannelsTask`, `video/TrickplayTileLoader`, `captionTask`, …) spawn during navigation. If they aren't released in `onDestroy`, or a single screen fans out many at once (a large-library grid), the count climbs toward the ceiling — the observed `&h29` crash in epic #728. The `ws://` socket-leak variant is fixed — `closeSocket()` STOPs the child on every reconnect (the accumulation path), with the vendored `WebSocketClientTask` loop's self-exit on CLOSED as the orphan backstop and `SignOut` stopping the published `socketNode` child at session teardown. The `HomeRows` latest-media fan-out is fixed — `home/LoadItemsTask` (one spawn per library) is replaced by a single `LoadLatestRowsTask` orchestrator that pools up to 3 concurrent requests regardless of library count. `photos/LoadPhotoTask` (a task that did no I/O — its whole body built a URL string) is removed outright, with `PhotoDetails` resolving the URL inline, dropping one type from the transient-task inventory. `QueueManager.launchShuffle` now calls `cancelActiveShuffleTask()` before spawning a new `GetShuffleItemsTask`, closing a double-launch hazard where a shuffle re-press before the first resolved left two tasks racing over the shared queue. `JRButtons`' `TextSizeTask` is now built per `buttons` write and released via `cancelTextSizeTask()` once `showButtons` has rendered, rather than held for the component's lifetime — the same prompt-release shape, but on a component that `extends="Group"`, so neither teardown plugin could ever have flagged it (see [`observe-without-on-destroy-jrscreen-only`](#observe-without-on-destroy-jrscreen-only)). That task could not simply be deleted the way `LoadPhotoTask` was: it needs `roFontRegistry`, a MAIN|TASK-only component the render thread cannot construct. Floor-audit, remaining transient-task bounding (grid/channel/trickplay tasks), and `onDestroy` enforcement remain open.
- **direction**: (1) Audit the persistent-task floor and keep it minimal — the pool is intentionally capped at 3 (`source/api/CLAUDE.md`: don't grow without measuring). (2) Bound remaining concurrent *transient* tasks. The `HomeRows` latest-media rows are done, and a sweep of every `CreateObject("roSGNode", "*Task")` site under `components/` + `source/` (2026-08-02) found **no remaining per-item Task fan-out** — no launch site currently scales with library size. This corrects an earlier claim here that the large-library grid was the next fan-out: `ItemGrid/LoadItemsTask2` was a *single* Task node making sequential blocking `fetchJson` calls, so its problem was latency on one thread, which `source/api/apiPipeline.bs` addresses and a thread bound would not. **Confirmed by measurement 2026-08-04** (n=4, Streaming Stick 4K, one movie library, 8 genres): the genre loop split **78% wait / 22% emit** — the inverse of Home's 51%-emit profile — so `apiPipeline` was the mechanism and the orchestration job pool would have attacked the wrong 22% while leaving the 757 ms of serial fetching untouched. **Shipped 2026-08-05**: the genre sample fetches now run through `apiPipeline`, keeping up to `apiPool.SLOT_COUNT` in flight on the one thread — 1081.5 ms → 603.5 ms task time (n=6, same device, both arms measured the same day). Mechanism is therefore chosen **per orchestrator from a measured split**, never carried across; see [`docs/dev/home-first-paint-performance.md`](../dev/home-first-paint-performance.md). What remains is the per-screen floor (each navigation spawns its own task nodes), not any one hot path. (3) Enforce that every routed screen's `onDestroy` releases its Task nodes (the `jrscreen-on-destroy` / `observe-without-on-destroy` BSC plugins already flag missing teardown — extend the discipline to explicit Task-node release). **Corrected 2026-08-14**: this assumed `onDestroy` runs at all, and for `/details/:type/:id`, `/library/:id` and `/search` it did not — `keepAlive` retained every POPPED instance for the session, so the sub never fired and each retained view kept its Task nodes, observers and textures (see [ADR 0029](../adr/0029-destroy-routed-screens-on-pop.md)). That half is closed and guarded by a census gate ([`tests/rta/specs/leaks.spec.js`](../../tests/rta/specs/leaks.spec.js)); what remains open is auditing each screen's `onDestroy` body for *complete* release. Note: the #744 `SideEffectTask` FIFO conversion is **task-count-neutral** — it stays a single Task; the per-request `ApiResultNode` children are plain Nodes (`extends="Node"`), not Task threads.

#### `no-lint-for-mlog-without-logger`

- **area**: [`scripts/lint/log-manager-init-check.js`](../../scripts/lint/log-manager-init-check.js), [`scripts/bsc-plugins/`](../../scripts/bsc-plugins/), any component codebehind calling `m.log.*`.
- **issue**: A component can call `m.log.warn(...)` while never constructing a Logger, and nothing catches it. `m.log` is then `invalid` and the call faults at runtime with `&hf3` ("Interface not a member of BrightScript Component") — a crash, not a silent no-op. `lint:log-manager-init` validates that the *manager* is stood up (`JRScene.init`), not that each component using `m.log.*` ever ran `m.log = new log.Logger(...)`. Found live in `components/home/HomeRows.bs`, which had a single `m.log.warn` on the latest-rows stall-reclaim path and no Logger anywhere in it or its `JRRowList` ancestor. It had never been seen because that path only fires when a run outlives its own budget; it surfaced immediately once a second `m.log` call was added to a path that runs every time. The failure mode is nasty precisely because it hides on rare branches — exactly the error-handling code you least want to fault.
- **direction**: A BSC plugin in the existing convention-plugin family (same `afterValidateFile` + AST visitor shape as [`no-direct-sdk.cjs`](../../scripts/bsc-plugins/no-direct-sdk.cjs) / [`no-raw-run.cjs`](../../scripts/bsc-plugins/no-raw-run.cjs)): flag any `m.log.<level>(...)` call in a file that contains no `m.log = new log.Logger(...)` assignment. Must account for inheritance — a codebehind may legitimately rely on an ancestor's `init` having set `m.log`, so resolve up the `extends` chain before flagging (both teardown plugins already walk `parentComponent`, so the machinery exists). Sweep first: run it as a warning to size the count before making it an error, since a wide first-run diagnostic count is likely.

  **Second check — argument count.** `Logger.info` is `function(message, value..value9)` — 10 params — and the `roku-log` plugin spends the first slot on the injected pkg path, so a call site may pass at most **nine**. Exceeding it is **not** a compile error (`npm run validate` passes clean); it faults at runtime with `Wrong number of function parameters` (`&hf1`), which drops the app into the BrightScript debugger and **hangs it mid-load**. That hang then presents as broken *tooling* rather than a bad log call — ODC requests time out, every ODC node read returns `undefined` so RTA nav helpers report "screen never loaded", and the UI sits on a spinner — which is what makes it expensive to diagnose.

  **This check does NOT need the new plugin above — it belongs in [`roku-log.cjs`](../../scripts/bsc-plugins/roku-log.cjs) itself.** That plugin already walks every log call (`isCallExpression` + `WalkMode.visitAllRecursive`), already holds `callExpr.args`, and already knows `config.insertPkgPath` — which is the exact +1 that makes the ceiling 9 rather than 10. The diagnostic is a few lines there, and the test harness exists (`transpile-with-plugin.js`, `roku-log.test.js`). Gate at the strictest bound (`> 9`) regardless of the current `insertPkgPath` setting: prod sets it `false`, but the fault surfaces on the dev builds people actually test with. The missing-Logger check above still wants the separate convention-plugin shape, because it needs to resolve up the `extends` chain and `roku-log.cjs` does no inheritance walking.

  **Evidence, and why this is High rather than Medium.** `components/ItemGrid/LoadItemsTask2.bs` shipped a 10-argument call that validated clean and faulted on device, costing most of a session (2026-08-04) before the device console — which names the offending file and line directly — was read. That was not a one-off: it recurs whenever a session adds a lot of logging, across months, and it is a *documented* rule that keeps being broken — which is the case for a gate rather than more prose. See the `.claude`-area followup in [`progress.md`](../progress.md) on auditing documented-but-unenforced rules; the sequencing there is enforcement first, doc tightening second.

#### `rooibos-setup-not-per-test`

- **area**: 23 spec files under [`tests/source/unit/`](../../tests/source/unit/) and [`tests/source/integration/`](../../tests/source/integration/) that build or mutate node state in `setup()`.
- **github**: #786 (epic — carries the per-file checklist; sub-issues spin off per group)
- **issue**: rooibos (`6.0.0-alpha.52`) runs `setup()`/`teardown()` **once per suite** and `beforeEach()`/`afterEach()` **once per test** — four distinct hooks on `BaseTestSuite`. 23 suites build their node in `setup()` and then mutate it, so each test inherits whatever the last one left behind; they pass on declaration *order*, not isolation. Confirmed in #781 while adding `Gradient.spec.bs`: a `rotateDegrees = 270` set by one test leaked into the next one *inside the same `@describe`*, which then resolved a different ramp asset and failed — the component was correct, the suite was not isolated. Per-describe grouping does not help. The visible-failure direction is the benign one; the hazard is the inverse — a test that never sets a field it depends on **passes on a neighbor's leftovers**, which is a green assertion of nothing that stays green until someone reorders or deletes that neighbor. It also inverts diagnosis: a leaked field makes a sound component look broken, which cost real time in #781 before the state was instrumented.
- **direction**: Move construction and any mutated state to `beforeEach()` (chaining `super.beforeEach()`), cleanup to `afterEach()`, and leave genuinely immutable per-suite fixtures in `setup()` — the goal is isolation for *mutated* state, not relocating everything. Audit rather than blind-rewrite: a suite where every test sets all the fields it reads is already order-independent. The cheap verification is to reverse the test order in the file and re-run — a suite that only passes in declaration order is the bug. Split by the epic's groupings, one reviewable PR each. Prevention already landed in [`tests/CLAUDE.md`](../../tests/CLAUDE.md), which auto-loads for anyone writing a spec.

#### `home-row-size-recompute-per-row`

- **area**: [`components/home/HomeRows.bs`](../../components/home/HomeRows.bs) — `setRowItemSize()`, and its callers `populateRowFromData` (re-insert branch), `removeRowAtIndex`, `insertLatestMediaSkeletons`, `onLibrariesLoaded`.
- **issue**: `setRowItemSize()` walks **every** row in `m.top.content` and rebuilds three parallel arrays (`rowItemSize`, `rowHeights`, `rowSpacings`), then writes all three to the `RowList`. It is called **once per row inserted** and **once per row removed**, so a Home load that touches N rows does N full walks, each ending in three more field writes to the `RowList` — quadratic in library count. This is the shape that hurts exactly the users epic #728 exists for: a library-rich server. Measured proxy on a Streaming Stick 4K with 11 libraries, forcing every latest row down the re-insert path: the render-side `other` column went 184 ms → **1067 ms**. The removal half is not hypothetical either — it fires for every library that returns no latest items, on every Home load. Not introduced by the #728 batching work; that work is simply the first time the path was measured.
- **direction**: Make the recompute run **once per batch of structural changes instead of once per change**. Cheapest shape is a dirty-flag + single flush at the end of the load pass (the drain loop in `onLatestRowsReady` already has the natural boundary); a more surgical option is to update only the changed index in the three arrays rather than rebuilding them, since `insertChild` at a known index makes the edit position known. Prefer whichever keeps `setRowItemSize()` the single owner of those three fields — the hazard to avoid is partial updates drifting out of sync with the row list. **Measure with the existing `attach`/`detach`/`other` split**: this lands in `other`, and the re-insert path is reachable on demand by disabling skeleton insertion. Surfaced by the #728 Home batching work.

- **area**: [`components/OverviewDialog.bs`](../../components/OverviewDialog.bs), [`components/OverviewDialog.xml`](../../components/OverviewDialog.xml)
- **issue**: `JRDialog` was restyled in #757 — buttons moved INSIDE the panel, a derived layout that measures each block instead of stacking fixed offsets, a short `colorSecondary` accent rule under the title rather than a full-width divider, and a spacing scale in multiples of 6 (so nothing goes fractional through the Roku OS downscale to 720p). `OverviewDialog` still has the original arrangement: fixed offsets, a full-width `colorBackgroundSecondary` divider, and its OK button OUTSIDE the panel. Shares the derived-layout helpers rather than re-deriving them.

#### `home-first-paint-scales-with-library-count`

- **area**: [`components/home/HomeRows.bs`](../../components/home/HomeRows.bs) (`populateRowFromData`), [`components/home/LoadLatestRowsTask.bs`](../../components/home/LoadLatestRowsTask.bs).
- **issue**: Even after the #728 batching fix, Home's render-side attach cost is **linear in rows × items** — one `appendChildren` per library row, 16 items each. Measured on a Streaming Stick 4K: ~315 ms of `attach` across 9 populated rows, ≈35 ms per row. That extrapolates to ~1.7 s at 50 libraries and ~3.5 s at 100, on the render thread, during first paint. Batching halved the per-item constant (~5.9 → ~2.2 ms/item) but did not change the growth. Every latest row is built and attached whether or not the user will ever scroll to it.
- **direction**: The structural answer is **viewport-lazy hydration** — attach items only for rows within (or near) the visible range, and fill the rest on scroll, keeping the skeleton rows as the placeholder they already are. Note this is the *same* mechanism already named as the correct fix for the Genres view's silent 100-genre truncation (see the open followup in [`docs/progress.md`](../progress.md)), so the two should be designed together rather than solved twice. Do **not** approach it by trimming the per-row item count — that changes what the user sees rather than when it is built. Sequencing: fix [`home-row-size-recompute-per-row`](#home-row-size-recompute-per-row) first, since it is a larger constant at realistic library counts and is a far smaller change. Surfaced by the #728 Home batching work.

#### `log-level-welded-to-debug-const`

- **area**: [`components/JRScene.bs`](../../components/JRScene.bs) (`initializeLogManager` call), the `manifest` `bs_const` line, [`scripts/harden-prod-manifest.js`](../../scripts/harden-prod-manifest.js).
- **issue**: The roku-log level is chosen by the `debug` compile-time const — `#if debug` → level 4 (everything), `#else` → level 2 (error/warn/info). So the only way to see `m.log.debug` / `m.log.verbose` output is to edit the `manifest`, flip `debug=true`, and rebuild. Two costs. **(1) You cannot raise verbosity without also changing the app.** `debug=true` attaches `rawApiData` to every transformed item (**+121 ms on a Stick 4K, +178 ms on a 512 MB Stick**, measured), arms failure injection, enables the toast cheat code, and turns on the Task-thread ledger — so anything observed while chasing a log line is observed in a distorted build. This is the same objection that forced `perfTiming` to be split out of `debug` rather than folded into it. **(2) It drives real churn on the committed manifest.** Flipping `debug` is a routine part of manual testing precisely because it is the only verbosity lever, and it has reached `main` as `true` twice (`27d99141` 2025-10-24, `dc05db8d` 2026-03-12), each reverted the same day — i.e. caught after landing, not before. `harden-prod-manifest.js` now guarantees no release artifact carries it, so the residual cost is DX and measurement fidelity, not a shipping hazard.
- **direction**: Two shapes, and the cheap one is a stepping stone to the expensive one rather than a complement — expect to delete it. **(A)** A dedicated `verboseLogging` const mirroring `perfTiming`: sets level 4 with no debug behaviors, registered in `FORCED_OFF`. ~4 lines plus manifest + doc, removes the distortion but keeps the edit-and-rebuild cycle, so it only solves half the problem. **(B)** Make the level settable at runtime so verbosity needs no rebuild at all — the shape that actually ends the churn, and the one worth designing properly. Open questions for (B): where the value lives (registry setting vs. an in-app dev affordance like the existing up-up-down-down toast chord), whether it survives a restart, and whether it is limited to dev builds. Note `initializeLogManager` cannot move earlier than `JRScene.init` (a platform constraint — see the comment there), so a runtime source must be readable at that point.

#### `observe-without-on-destroy-jrscreen-only`

- **area**: [`scripts/bsc-plugins/observe-without-on-destroy.cjs`](../../scripts/bsc-plugins/observe-without-on-destroy.cjs), [`scripts/bsc-plugins/jrscreen-on-destroy.cjs`](../../scripts/bsc-plugins/jrscreen-on-destroy.cjs)
- **issue**: Both teardown plugins hard-scope to descendants of `JRScreen` (`TARGET_BASE = 'JRScreen'`). Any SceneGraph component that isn't a routed screen — a `Group` or `LayoutGroup` reused as a widget — gets zero coverage. A sweep of `components/` found **45** non-`JRScreen` components with `observeField` calls that have no matching `unobserveField`. Most are self-observation (`m.top.observeField(...)`, which dies with the node and is benign), but the gap is real and had a live instance: `JRButtons` (`extends="Group"`) observed `width` on a `TextSizeTask` it created in `init()` and never released it, invisible to both plugins until it was found and fixed by hand during the task-hygiene work under #728. A second confirmed instance, and the first that is *cross-node* rather than self-observation: [`GridItem`](../../components/ItemGrid/GridItem.bs) observes the shared content root owned by its `BaseGridView` and calls `unobserveField` only when that root *changes*, never on teardown — it has no `onDestroy` at all. That closed a retain cycle (`view -> content root -> cell scope -> cached view node -> view`) which reference counting cannot collect. ADR 0029 mitigated it from the CONTAINER side (`BaseGridView.onDestroy` now drops the content root), so the cell-side gap is unchanged. **The shape is not one component's:** [`JRRowItem`](../../components/ui/rowitem/JRRowItem.bs) — and its `BrowseRowItem` subclass, the cell for `ExtrasRowList` and `SearchRow` — caches `m.contentRoot` and registers three scoped observers on it in a one-time `setupTextureObserver()`, with no `onDestroy` and no re-wire path at all. Its containers now diverge: `ItemDetails` cascades `m.extrasGrid.callFunc("onDestroy")` into `ExtrasRowList.onDestroy`, `SearchResults.onDestroy` drops `m.searchSelect.content` (added alongside ADR 0029, since that is what makes its teardown run at all), and nothing enforces that the next container remembers to do either. Container-side mitigation is per-container by construction, which is the argument for closing this at the cell.
- **direction**: Widen the target check to any SceneGraph component with a codebehind, not just `JRScreen` subclasses. The teardown *method* differs by class (`onDestroy` for routed screens; an explicit cancel/release sub for widgets with no lifecycle hook), so this likely needs a per-class allowlist of teardown methods rather than assuming `onDestroy` universally. Expect a large first-run diagnostic count — triage self-observation (benign) from cross-node observation (the real leak shape) before turning it on, or land it as a warning first.

#### `weblate-branch-stale-sync`

- **area**: Weblate integration (`locale/custom/*.json`, the Weblate branch/config).
- **issue**: The Weblate branch does not stay in sync with `main`. New `en_US` keys added on `main` don't reach Weblate for translators, and completed translations on the Weblate side don't flow back. Translation work drifts. NOTE: this is hygiene only — it is NOT the cause of the 216 untranslated keys in #641 (those strings exist in no source, Weblate included; syncing won't backfill them). See #641.
- **direction**: Restore bidirectional Weblate ↔ `main` sync (the Weblate GitHub integration / a scheduled merge) so new keys flow out and translations flow back automatically.

#### `loginflow-error-boundaries`

- **area**: `source/loginRouter.bs`
- **issue**: Every failure mode (server unreachable, server returned error, invalid/expired token, auth failed, password required) collapses into the same recovery: `routerNav("/server")` or `routerNav("/login")`. No category-specific handling — a transient network blip and a permanent auth failure both bounce the user back to server selection, losing their position in the flow. (Was `LoginFlow()`'s `goto startLogin` / `goto userSelect` in `showScenes.bs`; #677 moved it to the router without changing the collapse.)
- **direction**: Define a small set of error categories (network unreachable, server returned error, auth failed, token invalid) and a corresponding recovery flow per category. Network blips should retry-with-backoff; auth failures should drop into the user picker, not the server picker; token invalid should re-prompt for password without losing the server context.

#### `prelogin-intent-payload-coupling`

- **area**: `source/loginRouter.bs` (`onServerSubmitted`, `onCredentialsSubmitted`, `onUserSelected`), `source/main.bs` (`preLoginIntent` dispatch), the pre-login views (`components/config/SetServerScreen.*`, `components/login/UserSelect.*`, `components/config/LoginScene.*`).
- **issue**: The pre-login intent bridge is fire-and-forget: a view sets `m.scene.preLoginIntent = "<action>"` and main.bs drains it asynchronously, but each handler reads the intent's PAYLOAD off `getActiveView()` at DRAIN time rather than binding it to the intent at FIRE time. #### `per-item-cross-thread-appends`

- **area**: [`components/ItemGrid/BaseGridView.bs`](../../components/ItemGrid/BaseGridView.bs) (`rowsRoot.appendChild` in the genre branch), [`components/home/FavoritesRows.bs`](../../components/home/FavoritesRows.bs), [`components/extras/ExtrasRowList.bs`](../../components/extras/ExtrasRowList.bs), [`components/search/SearchRow.bs`](../../components/search/SearchRow.bs), [`components/liveTv/schedule.bs`](../../components/liveTv/schedule.bs). Fixed already in [`components/home/HomeRows.bs`](../../components/home/HomeRows.bs) — **both** of `populateRowFromData`'s branches.
- **issue**: A loop that appends N nodes one at a time into a row that is **already in the live render tree** is expensive in proportion to N, where one batched call is not. Measured on a Streaming Stick 4K in the Home latest-rows path: **~4.8 ms per item**, 849 ms of a 2646 ms first paint. Replacing the loop with `appendChildren` took that to 328 ms and first paint to 2129 ms (n=10/arm, complete separation, p=0.0002).
  **The mechanism is NOT established, and the earlier wording here overstated it.** This entry previously said the cost was "a rendezvous per `appendChild`" arising from thread ownership. Treat that as unproven: the appending code runs on the render thread, and rendezvous is a cost paid *from the Task side* — see [`threading.md`](threading.md) ("Task nodes are owned by the Render thread, so their fields rendezvous from the Task side"), and `rokudev/dev-doc` v2.0 `DEVELOPER/core-concepts/threads.md` upstream. Two things are measured and safe to rely on — the cost scales with the number of append **calls**, and it only appears when the **target is live in the render tree** (see direction). Don't re-derive a mechanism from the ownership model without new evidence.
- **direction**: For each site, establish whether the node being appended INTO is already attached to the rendered scene graph. Where it is, replace the loop with a single `appendChildren(array)`; where the target is still detached (built, then attached afterwards — the `ConfigList.setData` shape), there is likely nothing to win, so measure before changing. **Measure per site rather than sweeping** — the genre path carries ~8–23 appends against Home's 176, so it may not clear the ~120 ms resolution floor of the first-paint method. Note `LoadItemsTask2.bs:462` (a Task thread appending into its own not-yet-delivered node) is not a candidate on either reading. The `attach`/`detach`/`other` split now permanent in `HomeRows` is the instrumentation template. **Any claimed win must be checked against the live node counts**, because a run that renders fewer items looks identical in the timings: read the content tree off the device on both arms over ECP (the same `getChildCount()` / per-child field reads `tests/rta/` uses — row count, per-row tile count, and tile order) and require them to match exactly before believing a number. **What separates an expensive append from a free one is whether the target is LIVE in the render tree.** Measured on the same device and session by forcing every latest row down the re-insert branch (skeleton insertion disabled, so `detach = 0` proves the path was taken): the identical `appendChildren` of the same items costs **~315 ms into a live row and ~0 ms into a still-detached one** (n=8 vs n=6). The items really do arrive — verified on screen, since an empty run would also report ~0. **This does not make "build detached" a fix**: that same arm ran *slower* end to end (total 2083 → 3266 ms), with `other` absorbing +884 ms. Where the work actually goes, and why, is not established — that arm also does per-row `CreateObject` / `insertChild` / `setRowItemSize` the in-place path never does, and this experiment cannot separate the two. The actionable part needs neither answer: **`attach` alone can mislead**, because a site appending into a detached node reports ~0 whether or not it is optimal. Decide on `total`, not on the column. Surfaced in the #728 Home batching work.

- **area**: `source/api/apiPromise.bs`, `source/api/apiPool.bs`
- **issue**: JellyRock deliberately runs two async models at once: promises (`fetchAsync`) on the render thread, and blocking `fetchRes` / `fetchJson` inside Task threads for the bootstrap path and linear/branching orchestrators (`components/tasks/QuickPlayTask.bs`, `LoadItemsTask`, `source/api/items.bs`). This is the intentional Option A split from decision `promise-native-interface-fetchres-exception` — not an accident, but a tracked divergence to revisit.
- **direction**: Collapse to a single promise model once BrighterScript **async/await** ships — `await fetchAsync(...)` restores the linear/branching readability that today justifies keeping blocking `fetchRes` in Task orchestrators. Re-open decision `promise-native-interface-fetchres-exception` at that point and, in the same pass: **(a)** convert kept-Task internals (`components/tasks/QuickPlayTask.bs`, `ItemGrid/*`, `liveTv/*`) from blocking `fetchRes` to `await fetchAsync`; **(b)** parallelize each remaining orchestrator's *independent* fetches via `await promises.all([...])` — a deferred perf opportunity that today's `wait2` machinery makes not worth the regression risk. Note `home/LoadLatestRowsTask` (which replaced the per-library `home/LoadItemsTask`) is off both lists: `source/api/apiPipeline.bs` is a third pattern — non-blocking `submitApiRequest` plus a bounded wait, still one Task thread — that already runs its N independent fetches concurrently without waiting on async/await. **2026-08-05: `ItemGrid/LoadItemsTask2`'s per-genre sample fetches moved onto that same third pattern**, so `ItemGrid/*` is on list (a) only for its remaining blocking call — the single main item query in `executeItemQuery` — not wholesale; **(c)** non-pool HTTP (fonts / captions / SSDP via raw `roUrlTransfer`) — **resolved 2026-06-06: declined**, decoupled from the async/await trigger. These three are Task-thread datagram/binary/time-budgeted flows, not render-thread pool consumers, so they stay blocking Tasks with no generic wrapper (rationale: wrong layer / `&hf3` regression risk on `captionTask` / no shared shape + no auto-abandon fit — see decision `non-pool-http-stays-task-blocking`). Only items (a)/(b) remain open, against the async/await trigger. Until then the split is correct; do NOT preemptively rewrite working orchestrators into `wait2` promise-loops (negative readability, regression risk on hot paths).

#### `legacy-print-statements`

- **area**: 14 component `.bs` files (`components/tasks/*Task.bs`, `components/ui/**`, `components/Buttons/JRButtons.bs`, `components/home/HomeRows.bs`, `components/search/SearchResults.bs`, `components/video/VideoPlayerView.bs`) plus `source/data/JellyfinDataTransformer.bs`. Existing legacy sites are opted out; the plugin still catches new violations in clean files.

#### `sd-resolution-native-support`

- **area**: `manifest`, `scripts/generate/icons-build.js`, `images/icons/*_sd.png`
- **issue**: Native SD assets aren't shipped (the `_sd` slot in `uri_resolution_autosub=$$RES$$,sd,hd,fhd` is reserved but unused) because correct rendering requires NTSC pixel-aspect-ratio handling — SD framebuffer pixels are non-square (720×480 with 8:9 or 32:27 SAR depending on 4:3 vs 16:9 output mode). A naive square-pixel SD render via sharp would produce horizontally-squished icons that may look worse than what the OS produces by auto-scaling. Not gated on any layout refactor: hardware verification (2026-08-07, #419 closing comment) showed `$$RES$$` substitution keys off the *device's* UI resolution even under `ui_resolutions=fhd` — a 720p device loads the `_hd` triples (seen directly in `r2d2_bitmaps`) — so an `_sd` asset would be picked up by SD devices today. (This entry previously cited a `hd-native-layout-refactor` blocker; that slug's premise was disproven by the same verification and it has been retired — see Recently removed.)
- **direction**: If SD becomes a meaningful target: extend `scripts/generate/icons-build.js` with a render path that compensates for the non-square SAR. Empirically verify on hardware: set Roku Display Type to `480p`, sideload, compare a candidate hand-authored SD asset against the OS-produced fallback. Ship native SD only if measurably better. If not, leave the `_sd` slot empty (autosub falls through to `hd` per Roku spec) and document the decision. Promote severity to Medium if SD-specific user reports surface.

#### `nul-bytes-in-scripts-source`

- **area**: `scripts/**/*.{js,cjs}`; a guard would live in `scripts/lint/`.
- **issue**: A raw literal NUL (`\x00`) byte used as an in-memory join separator for a sort/group key has been committed into a `scripts/` source file twice — first in [`scripts/generate/findings-candidates.js`](../../scripts/generate/findings-candidates.js) (`opKey`), then in [`scripts/generate/spec-diff.js`](../../scripts/generate/spec-diff.js) (`changeSortKey`, fixed in `a4a92e78`). A raw NUL makes git + `file(1)` classify the source as **binary**, so it lands with no reviewable diff. Both were semantics-preserving (the separator is sort-only, never persisted) and both are now fixed to use the `'\0'` escape, but nothing prevents a third occurrence — no lint rejects control bytes in `scripts/` sources (ESLint's `no-control-regex` is regex-only; Prettier passes a file containing a NUL clean).
- **direction**: Add a CI-gated lint (e.g. `scripts/lint/no-control-bytes.cjs`) that fails when any `scripts/**/*.{js,cjs}` file contains a NUL or other control byte outside tab/newline; wire it into `npm run lint` + pre-push. The fix it enforces is always the same — use the `'\0'` string escape, never a literal control byte.

#### `exit-net-summary-lost-on-macos-pipe`

- **area**: [`scripts/run-record.js`](../../scripts/run-record.js) (`armCloseOnExit`) — the `process.on('exit')` net that folds a device run its entry point never closed.
- **issue**: That net prints the run summary with `console.log` from inside a Node `exit` handler, which is only safe because stdout writes are synchronous there. That holds for TTYs, files and pipes on Linux (and for CI), but **stdout writes to a pipe are asynchronous on macOS** — so a macOS contributor who pipes an interrupted run (`npm run test:rta | tee log`) can lose the printed summary on Ctrl-C. Nothing durable is lost: the fold itself is `fs.writeFileSync` / `fs.appendFileSync`, so `run-meta.json` and the `.device-runs/<kind>/runs.jsonl` ledger both land regardless — only the terminal narration goes missing, and every field it renders is present in the JSON. The net exists precisely because the interrupt path cannot fold itself (three of four entry points hand their exit to a signal handler ending in `process.exit()`), so moving the fold off that path is not an option.
- **direction**: Only worth doing if a macOS contributor actually reports a missing summary — the failure is cosmetic and the recovery (read `run-meta.json`) is one command. If it does bite, have the exit handler write the rendered summary lines into the run record as a `summaryLines` array and have the entry point print them on the next invocation, or teach `npm run device:status` to render the last run's summary; either sidesteps the asynchronous `stdout` pipe behavior on macOS entirely without re-introducing an async write on the exit path.

#### `remotecontrol-socket-abrupt-teardown`

- **area**: `source/api/userAuth.bs` (`SignOut`), `components/remotecontrol/RemoteControlTask.bs`
- **issue**: `SignOut` stops the remote-control receiver with `m.global.remoteControlTask.control = "STOP"`, which terminates the Task thread outright before the active transport is gracefully torn down. On the `ws://` path (#666) the socket is not gracefully closed (no `WebSocket` close handshake); on the `https` long-poll path (#667) an in-flight poll `roUrlTransfer` (held up to `POLL_TIMEOUT_MS`, ~35 seconds) is abandoned mid-call rather than `AsyncCancel`ed. Both are functionally harmless: Jellyfin reaps the orphaned session on its inactivity timeout (or the plugin's poll-freshness grace window lapses), and the token is invalidated by the same `SignOut`. But each leaves a briefly-dangling resource on every logout / server switch.
- **direction**: Have the receiver observe a shutdown signal (or check a flag in its loop) and tear the active transport down gracefully before exiting — `close = [1000]` on the `WebSocketClient` for the socket path, `AsyncCancel` on the outstanding poll for the long-poll path — so `SignOut` requests a graceful close instead of an abrupt thread kill. Low priority; only matters if a lingering half-open socket / abandoned transfer ever proves observable. Note: `SignOut` now also STOPs the live socket child (abruptly) via the `socketNode` field `RemoteControlTask` publishes — that field is the handle the `close = [1000]` half of this direction would use, so the socket path no longer needs a new plumbing mechanism, only the graceful sequencing. `closeSocket()` briefly carried a `close = [1000]` request; it was **removed** rather than kept as scaffolding, because it ran only after the client had already left `OPEN` (nothing to send) and was followed on the next line by the `STOP` that kills the delivering thread. Re-adding it is one line if this is ever done for real; what the graceful path actually needs is the *sequencing* (request close, wait for the handshake or a timeout, then STOP), not the call site.

#### `videoplayerview-teardown-guard-partial`

- **area**: `components/video/VideoPlayerView.bs`
- **issue**: #733 fixed a teardown race in `onPositionChanged` by checking `m.isDestroyed` (set at the top of `onDestroy`) before dotting into notification refs. The same class of race — a native-engine or Task callback firing after `onDestroy` starts but before `unobserveField` actually detaches it — is structurally possible for the other observers `onDestroy` tears down (`state`, `content`, `selectedSubtitle`, `audioIndex`, `mediaSourceId`, `shouldAllowCaptions`, `subtitleTrack`, `globalCaptionMode`, the `playbackTimer`/`bufferCheckTimer` `fire` callbacks, and task `content`/`refreshedItem`/`currentCaption`). Only the proven crashing path was guarded (isolate-the-fix); the others are unguarded but unobserved.
- **direction**: If another handler in this set turns up in a crash report with the same shape (a torn-down ref accessed during teardown), add an early `if m.isDestroyed then return` to that handler rather than re-diagnosing from scratch. A blanket guard on every handler is deliberately *not* applied up front — only proven crash sites warrant it.

#### `api-usage-manifest-no-per-endpoint-binding`

- **area**: [`docs/architecture/api-usage-manifest.json`](api-usage-manifest.json), [`scripts/generate/api-usage-manifest.js`](../../scripts/generate/api-usage-manifest.js)
- **issue**: `requestFields` is flat and repo-wide (`{name, sourceFiles}`, no endpoint association) and its `REQUEST_FIELD_GLOBS` scan covers `source/api/**/*.bs` only — narrower than the endpoint scan's `source/**` — so it can't compare the params we send against the params an endpoint declares, and can't see `components/**` (or `source/data/`, `source/utils/`) call sites. #784 hit both blind spots at once — see [Known limitations](server-upgrade-automation.md#known-limitations--what-this-pipeline-cannot-catch).

#### `ci-path-filters-unverified`

- **area**: the `paths` filter in each `.github/workflows/_lint-*.yml` / `_test-*.yml`, plus [`scripts/lint/ci-parity-check.js`](../../scripts/lint/ci-parity-check.js)
- **issue**: `lint:ci-parity` proves every `npm run lint` check is invoked by **some** workflow, but nothing verifies that workflow's hand-authored `paths` filter actually matches the files the check reads. A filter that is too narrow passes `lint:ci-parity` (the check does have a CI home) while never firing on the PR that needed it — the same silent-no-gate outcome the parity check was written to prevent, one layer down. Two live examples of how easily a filter goes stale: `_lint-spelling.yml` matched only `\.md$` while `lint:dictionary`'s real input is `dictionary.txt`, and `_lint-floor-system.yml` matched the generated `api-usage-manifest.json` but not the generator that produces it — both widened by hand in the same PR that added the parity gate. Two more remain live and were left alone deliberately (they belong to checks this PR did not wire): `_lint-brightscript.yml` does not match `scripts/lint/socket-auth-binding-check.js`, so a PR weakening that check does not re-run it, nor `bsconfig.json`, which is a real input to `npm run validate`. Also note `_test-scripts.yml` is filtered to `^scripts/|^tests/scripts/|^images/gradients/|^vitest\.config\.js$|^package(-lock)?\.json$` — the `images/gradients/` clause was hand-widened in #777 so `gradient-assets.test.js` catches an edit that touches only a ramp PNG and lands without a generator change, a third live instance of the same by-hand pattern — so a Vitest test asserting against **app** source (as `apiversion-consistency.test.js` and `socket-auth-binding.test.js` both do) still does not re-run when that app source changes; the lint script is the gate there, and the Vitest test is the test *of the script*.
- **sibling layer, also unverified**: whether the hosting workflow's status-check context is a **required** check on `main`. A check in a non-required context runs and reports red but does not block a merge — the same silent-no-gate outcome, one layer further out again. This was live: `floor-system` and `issue-templates` were both absent from branch protection, leaving `lint:endpoint-availability`, `lint:floor-coverage`, `lint:apiversion-consistency`, `lint:issue-templates` and `docs:api-manifest:check` (wired by this very PR) running without gating. Both contexts were added to the required list; the *invariant* stays unenforced because branch protection is repo configuration rather than a file in the tree, and reading it needs admin scope CI's `github.token` lacks. Documented as a manual step in [build-and-tooling.md](build-and-tooling.md).
- **direction**: Have each check declare the globs it reads (a small export, or a manifest keyed by npm script name) and extend `ci-parity-check.js` to assert the hosting workflow's `paths` filter is a superset. That needs a glob-vs-regex comparison, since the filters are regular expressions fed to `changed-paths` while the inputs are naturally globs — likely the reason to do it as a normalization step rather than exact matching. The required-check layer would need either a committed list of expected contexts (which drifts on its own) or a PAT with admin scope in CI; neither is obviously worth it, so the doc note is the fix for now. Medium: the failure is silent and the parity gate's existence makes it easy to assume this is already covered.

#### `rta-run-scope-unrecorded-in-ledger`

- **area**: [`scripts/run-record.js`](../../scripts/run-record.js) (`beginRun`, `summarizeRun`), read by [`scripts/flake-baseline.js`](../../scripts/flake-baseline.js)
- **issue**: `variant` records the npm script that was invoked (`test:rta` / `test:rta:fast`), not the test scope that actually ran. `rta-run.js` forwards passthrough args to Vitest, so `npm run test:rta:fast -- -t "moviesLibraryGenres"` runs ONE test and appends a ledger line identical in shape to a full 38-test suite — same `variant`, same `outcome`, same `commit`/`dirty`/`deviceKey`. A baseline selection cannot tell them apart, so a scoped debugging run silently joins the population and is counted as a clean sample. Hit live on 2026-08-12: three targeted single-screen runs were taken to establish whether a failure was deterministic, and each wrote a line that `flake-baseline` would have counted as a full green suite. It did no harm only because the pending PRs moved `HEAD`, so the commit filter excluded them by accident rather than by design.
- **not the already-declined per-test counts**: [`outcomes-partition-into-samples`](../decisions.md) deliberately rejected storing per-test pass/fail counts — "one field that cannot disagree with itself, and the baseline's question is run-level". That still holds and this does not reopen it. The gap here is the run's declared SCOPE, not per-test results: a one-line `scoped: true` (or the filter pattern) answers it without the ledger ever describing individual tests.
- **direction**: Detect a scope filter from the invocation — `rta-run.js` already computes `passthrough` (`process.argv.slice(2)` minus `--watch`), so a `-t` / `--testNamePattern` present there is readable at `beginRun` with no new plumbing — and stamp it into the record. Then `flake-baseline` excludes scoped runs by default and attributes them like its other exclusions (`N scoped run`). Low: today's protection is operator discipline ("don't feed a `-t` run into a baseline"), which is exactly the kind of unwritten rule the ledger's other filter keys exist to replace.

#### `measure-single-device-only`

- **area**: [`scripts/measure.js`](../../scripts/measure.js) (`setupRtaEnv()` / `ROKU_IP`), [`scripts/measure-args.js`](../../scripts/measure-args.js)
- **issue**: `npm run measure` drives exactly one device, read from `ROKU_IP`. A cross-tier comparison therefore means re-exporting `ROKU_IP` and invoking the tool once per device by hand, and nothing in the repo tells a contributor which devices exist — the addresses live in one maintainer's `.env`. This is the same shape as the already-filed `docs` followup about the public docs keying their instructions on one maintainer's LAN addresses, and the two want the same fix. It bit immediately: the first multi-device run measured `.176` and `.178` against the DEMO server (3 rows) and `.177` against the real one (10 rows), which read as "the 512 MB Stick is nearly twice as fast as the 1 GB Stick 4K" until the `rows` column was checked. The per-line data to disambiguate a matrix already exists — the record carries device model, model number and Roku OS — so only the driving loop and the tier label are missing.
- **direction**: **The tier-label half is DONE, and is now a generated dataset rather than a hand-typed map.** [`scripts/data/roku-hardware.json`](../../scripts/data/roku-hardware.json) is derived from Roku's published spec (rokudev/dev-doc `SPECIFICATIONS/hardware.md`) by [`roku-hardware.js`](../../scripts/generate/roku-hardware.js) and read through [`roku-devices.js`](../../scripts/roku-devices.js); every measurement record carries `ramTier`, and `npm run measure:compare` REFUSES to compare two arms across tiers rather than leaving it to a reader to notice. The first cut WAS a hand-typed map, and it is worth recording why that was not enough: it keyed on four DIGITS, so all sixteen letter-prefixed Roku TV and Projector families (`J000X`, `A000X`, `K8PXX` — 512 MB to 2 GB) resolved to `null` forever, and it could not notice that upstream had added a device. The key is now the four-CHARACTER family, because `.177` reports `3820RW`, a model number in no Roku table while its family is; that no family carries two RAM values is re-asserted on every generate rather than checked once. A weekly [sync workflow](../../.github/workflows/roku-hardware-sync.yml) opens a PR when the data moves. See [`roku-device-dictionary-generated`](../decisions.md#decision-id-roku-device-dictionary-generated). **What remains is the driving loop**: an optional `ROKU_DEVICES=<ip>,<ip>,<ip>` in `.env`, leaving `ROKU_IP` as the single-device default so nothing breaks. The original split still holds and half of it now exists — `.env` declares which devices EXIST, the dataset declares what tier a model IS, so a contributor lists only their own addresses and gets correct labels for free. Low: a matrix is runnable today, one `ROKU_IP` export per device, and each line now self-describes its tier. **2026-08-16 — the loop the driver would iterate is now extracted**: [`scripts/measure-loop.js`](../../scripts/measure-loop.js) takes every impure collaborator as an injected dependency (clock, sleep, relaunch, nav, the console window and its reader, log) and is covered by [16 tests](../../tests/scripts/unit/measure-loop.test.js). This does NOT close the entry — `ROKU_DEVICES` parsing and the driving loop still do not exist — but it removes what would have been the awkward half of writing them: threading a per-device loop through code that also owned the console socket and the reporting inline. A nav failure now throws rather than exiting, so one device failing no longer kills the rest of a matrix, and `NavFailedError` carries the launches that device had ALREADY taken — a driver that has to drop the device should not also drop its good samples. Two further properties the driver inherits rather than re-derives: the quiet-break ignores any stamp older than the launch's own window, so a per-device reader is not required to reset a clock it does not know about; and the refusal text is built at the throw site, so a driver reporting one device's failure prints what the single-device tool prints.
