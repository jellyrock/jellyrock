# Tech Debt & Cruft

A living inventory of known issues, plus a "recently removed" list (so future-you doesn't waste time searching for ghosts that have been deleted).

For *what's good and shouldn't be casually reformed* — see the relevant topic doc in [`docs/architecture/`](./README.md#topic-map--load-by-purpose). Each topic doc explains its subsystem's design intent inline, where the context is fresh.

Each refactor item has a stable slug for cross-referencing in commits, PRs, and GitHub issues. When a slug is filed as a GitHub issue, add the issue number as the `github` field. When the work is complete, remove the entry entirely (the closed GitHub issue becomes the historical record).

## How to use this document

- **Considering a refactor?** Check this list first. If the area is here, the change is at least documented; pick severity carefully — `low` items are usually quirks with reasons.
- **Considering a major change to a "clean" subsystem?** Read the relevant topic doc in [`docs/architecture/`](./README.md) first. The clean systems are clean for reasons that aren't always obvious from the code alone, and those reasons live in the topic docs (e.g., the persistent task pool's children-as-vehicle dodge for SceneGraph event coalescing is in [`api.md`](./api.md), the DoVi `buffer:loop:` retry is in [`playback.md`](./playback.md)).
- **Filing a GitHub issue?** Reference the slug in the title and link from the issue back to this entry. Add the issue number to the entry's `github` field here.
- **Fixing an entry?** Remove the entry from this file in the same PR. The git history of this file becomes the audit trail of what got fixed when.

### Citing a slug from another doc / comment

Use the **anchor-link form**, not narrative prose:

```markdown
[`manual-theme-cascade`](../../docs/architecture/tech-debt.md#manual-theme-cascade)
```

In code comments / diagnostic strings (where markdown won't render), use the bare anchor: `tech-debt.md#manual-theme-cascade`.

The `npm run lint:docs` checker validates every `tech-debt.md#<anchor>` reference against the actual headings in this file, so deleting a slug catches stale references at push time. Naked narrative mentions like `` `manual-theme-cascade` `` (no anchor) are not checked — there's no syntactic signal to distinguish them from any other backtick-wrapped kebab-case identifier — so the convention exists to keep the check bulletproof. If you find yourself mentioning a slug, link it.

## Severity rubric

- **High** — meaningful complexity costs; fixing genuinely improves agent + human DX. Worth scheduling.
- **Medium** — worth refactoring when adjacent (touch the area for any reason → fix in passing).
- **Low** — minor irritants, low blast radius. Often quirks with rationale; fix only if the surrounding work makes it cheap.

## Refactor candidates

### High

#### `itemdetails-size`

- **area**: `components/ItemDetails.bs`
- **issue**: Single file handles **16 distinct item types** via per-type `populateInfoGroup<Type>` renderers (Movie, MusicVideo, Episode, Series, BoxSet, Season, Person, MusicArtist, MusicAlbum, Playlist, Audio, Photo, PhotoAlbum, TvChannel, Program, Recording). 3,600+ lines, ~90 top-level functions, 100+ line `onKeyEvent`. Extras pane animation logic (grid + gradient overlay + slide interpolators) interleaved with Task-result handlers; the inline `TrackDropdown` cluster (~20 functions for pre-playback audio/subtitle/source selection) is also embedded here.
- **direction**: Split per item-type renderer (`populateInfoGroupMovie`, `populateInfoGroupSeries`, etc.) into separate modules under `source/details/` or `components/details/`. Extract: (a) the extras pane (animation + grid + gradient overlay) into its own component, (b) the `TrackDropdown` cluster into its own component (already self-contained — wire via fields), (c) the resume button + logo/date-label clusters as smaller helpers. `onKeyEvent` shrinks naturally as each subsystem owns its own focus / key handling.

#### `videoplayerview-size`

- **area**: `components/video/VideoPlayerView.bs`
- **issue**: 2,119 lines, 67 top-level functions, 133-line `onKeyEvent`. Mixes native `Video` event handling, the playback state machine (`onState`), OSD action dispatch, trickplay, transcoding decisions, the DoVi `buffer:loop:` retry flow, subtitle management (~8 fns), chapter navigation (~4 fns), audio/source track switching (~4 fns), next-episode + media-segment notifications (~10 fns — the largest embedded subsystem), Live TV / DVR-recording mode (~8 fns: channel switching, EPG refresh, live-edge math), and Jellyfin reporting.
- **direction**: Extract subsystem controllers, each owning its own observers + key handling: `SubtitleController` (~8 fns), `ChapterController` (~4 fns), `TranscodeRecoveryHandler` (DoVi retry + error dialog + force-finish, ~6 fns), `NotificationController` (next-episode + media segments, ~10 fns), `LiveTvController` (~8 fns — trickiest because it couples tightly with the underlying `Video` state machine; extract last). The player class is left with lifecycle, state-machine observation, OSD dispatch, audio/source switching, trickplay UI sync, and reporting.

#### `mainbs-event-loop-fan-out`

- **area**: `source/main.bs`
- **issue**: 414-line file (down from 1,315 as of #677 — the #550 sgRouter migration removed the search, audio `playItem`, `optionSelected`, and `closeSidePanel` branches plus their inline logic; the dead resume/start-over playback-options flow was deleted in #757; the #288 phase-3 dialog migration deleted the `isDataReturned` branch, and its phase-4 Quick Connect rebuild deleted the `isAuthenticated` and `close` branches — that flow no longer reaches the main thread until it has a finished session). `Main()` still spans the whole file: bootstrap (Phase 1 globals → migrations → theme → login → Phase 2 globals) then the main event loop (`roSGScreenEvent` screen-closed, `exit`, `preLoginIntent`, `isFontDownloadCompleted`, `reachable` server-probe, `userMenuAction`, `roDeviceInfoEvent`, `roInputEvent` deep-link, `result` dialog-return, `reloadHomeRequested`). Some heavy work is extracted into `handle*` helpers (font, menu, login). The dialog fan-out is **gone**: the former `isDataReturned` branch is a one-line delegation to `onServerSwitchDialogResult`, and it stays one line because the identity check that makes a second main-thread dialog safe lives with the flow that owns it, not here.
- **direction**: What remains is the BOOTSTRAP half — Phase 1/2 globals, migrations, theme and login sequencing are still inline in `Main()`. Extract to `source/bootstrap.bs` so `Main()` becomes `bootstrap()` + a thin dispatch loop. The `source/handlers/dialogs.bs` extraction this entry used to call for is **no longer wanted**: with one main-thread dialog claimant there is nothing to fan out, and a registry for one entry would be machinery without a second consumer. Revisit only if a second main-thread flow starts observing `result` on the port.

#### `task-thread-budget`

- **area**: `components/**/*Task.*` (26 Task component types), `source/utils/globals.bs`, `source/main.bs`, plus `JRScreen` `onDestroy` teardown across routed screens. Per-item fan-out itself is now guarded structurally by [`scripts/bsc-plugins/no-task-fanout.cjs`](../../scripts/bsc-plugins/no-task-fanout.cjs) (Error severity).
- **github**: #728 (crash manifestation — `&h29` "Too many task threads" on large libraries)
- **issue**: Roku OS caps concurrent Task threads at **50 (soft) / 100 (hard)** per app. JellyRock runs a fixed floor of ~5 persistent API-tier tasks (3× `ApiTask` pool + `ApiQueueTask` coordinator + `SideEffectTask`), plus `RemoteControlTask` (and a nested `WebSocketClient` task on the `ws://` path) and the two font tasks. On top of that floor, transient per-screen tasks (`ItemGrid/LoadItemsTask2`, `tasks/QuickPlayTask`, `ItemGrid/LoadVideoContentTask`, `liveTv/LoadChannelsTask`, `video/TrickplayTileLoader`, `captionTask`, …) spawn during navigation. If they aren't released in `onDestroy`, or a single screen fans out many at once (a large-library grid), the count climbs toward the ceiling — the observed `&h29` crash in epic #728. The `ws://` socket-leak variant is fixed — `closeSocket()` STOPs the child on every reconnect (the accumulation path), with the vendored `WebSocketClientTask` loop's self-exit on CLOSED as the orphan backstop and `SignOut` stopping the published `socketNode` child at session teardown. The `HomeRows` latest-media fan-out is fixed — `home/LoadItemsTask` (one spawn per library) is replaced by a single `LoadLatestRowsTask` orchestrator that pools up to 3 concurrent requests regardless of library count. `photos/LoadPhotoTask` (a task that did no I/O — its whole body built a URL string) is removed outright, with `PhotoDetails` resolving the URL inline, dropping one type from the transient-task inventory. `QueueManager.launchShuffle` now calls `cancelActiveShuffleTask()` before spawning a new `GetShuffleItemsTask`, closing a double-launch hazard where a shuffle re-press before the first resolved left two tasks racing over the shared queue. `JRButtons`' `TextSizeTask` is now built per `buttons` write and released via `cancelTextSizeTask()` once `showButtons` has rendered, rather than held for the component's lifetime — the same prompt-release shape, but on a component that `extends="Group"`, so neither teardown plugin could ever have flagged it (see [`observe-without-on-destroy-jrscreen-only`](#observe-without-on-destroy-jrscreen-only)). That task could not simply be deleted the way `LoadPhotoTask` was: it needs `roFontRegistry`, a MAIN|TASK-only component the render thread cannot construct. Floor-audit, remaining transient-task bounding (grid/channel/trickplay tasks), and `onDestroy` enforcement remain open.
- **direction**: (1) Audit the persistent-task floor and keep it minimal — the pool is intentionally capped at 3 (`source/api/CLAUDE.md`: don't grow without measuring). (2) Bound remaining concurrent *transient* tasks. The `HomeRows` latest-media rows are done, and a sweep of every `CreateObject("roSGNode", "*Task")` site under `components/` + `source/` (2026-08-02) found **no remaining per-item Task fan-out** — no launch site currently scales with library size. This corrects an earlier claim here that the large-library grid was the next fan-out: `ItemGrid/LoadItemsTask2` was a *single* Task node making sequential blocking `fetchJson` calls, so its problem was latency on one thread, which `source/api/apiPipeline.bs` addresses and a thread bound would not. **Confirmed by measurement 2026-08-04** (n=4, Streaming Stick 4K, one movie library, 8 genres): the genre loop split **78% wait / 22% emit** — the inverse of Home's 51%-emit profile — so `apiPipeline` was the mechanism and the orchestration job pool would have attacked the wrong 22% while leaving the 757 ms of serial fetching untouched. **Shipped 2026-08-05**: the genre sample fetches now run through `apiPipeline`, keeping up to `apiPool.SLOT_COUNT` in flight on the one thread — 1081.5 ms → 603.5 ms task time (n=6, same device, both arms measured the same day). Mechanism is therefore chosen **per orchestrator from a measured split**, never carried across; see [`docs/dev/home-first-paint-performance.md`](../dev/home-first-paint-performance.md). What remains is the per-screen floor (each navigation spawns its own task nodes), not any one hot path. **Enforced 2026-08-22**: that sweep was a point-in-time finding, not a standing guarantee — [`no-task-fanout.cjs`](../../scripts/bsc-plugins/no-task-fanout.cjs) now makes a `launchTask()` inside a loop body a compile-time **Error** unless its argument is a stable dotted path rooted at `m` that the loop body does not rebind, so a future PR cannot silently reintroduce the #728 shape. Validated against the real crash rather than a synthetic case: run over `HomeRows.bs` as it stood at `c59e96a1^` — with that file's raw `control = "RUN"` writes rewritten to the `launchTask()` form, since the `no-raw-run` migration came later — it reports exactly one diagnostic, the per-library `launchTask(loadLatest)`, and leaves the six in-loop `m.LoadXTask` launches in that same file alone. The rebind half of the rule is what stops the obvious escape: parking a freshly built node in an `m.` field each turn is the same fan-out wearing a stable name. Two residual gaps are accepted rather than tracked, both needing call-graph analysis to close: a loop calling a helper that launches internally, and a local aliased to a stable `m.` slot before the loop (flagged though safe). **A third gap is structural rather than interprocedural: the rule engages on a LOOP, so repetition driven by a TIMER or an observer is invisible to it — and so is the runtime ceiling above, for a different reason.** `QuickConnectDialog` as it stood before #847 built a fresh `QuickConnect` Task node on every 3-second timer tick and launched it, roughly a hundred launches across a five-minute wait. Running the plugin over that file reports **0** diagnostics against **1** on a control fan-out through the same harness, so the loop rule genuinely does not reach it. **But it was CHURN, not concurrency, and that distinction is the point**: each poll stopped its task before the next tick, so live threads stayed at ~1 and `TASK_THREAD_WATERMARK` would never have fired either. It was waste — a hundred thread creations for work one node could have done — rather than a step toward `&h29`, and an earlier draft of this entry (and of #847's commit message) called it a fan-out of the #728 class, which overstates it. No live instance remains: #847 replaced that poll with a render-thread promise. Recorded because the two guards above are complementary and neither covers this shape, so the next timer-driven launch will be caught by nobody — not because it would exhaust the cap, but because nothing will say it is wasteful. (3) Enforce that every routed screen's `onDestroy` releases its Task nodes (the `jrscreen-on-destroy` / `observe-without-on-destroy` BSC plugins already flag missing teardown — extend the discipline to explicit Task-node release). **Corrected 2026-08-14**: this assumed `onDestroy` runs at all, and for `/details/:type/:id`, `/library/:id` and `/search` it did not — `keepAlive` retained every POPPED instance for the session, so the sub never fired and each retained view kept its Task nodes, observers and textures (see [ADR 0029](../adr/0029-destroy-routed-screens-on-pop.md)). That half is closed and guarded by a census gate ([`tests/rta/specs/leaks.spec.js`](../../tests/rta/specs/leaks.spec.js)); what remains open is auditing each screen's `onDestroy` body for *complete* release. **Corrected 2026-08-22**: this item's framing assumed #728 was itself an `onDestroy` / teardown gap. It was not. The removed `HomeRows.bs` fan-out had *correct* teardown — `cleanupLatestMediaTasks()` stopped and unobserved every task, both before a new run and on destroy — and still produced the crash, because the crash was concurrent launches **within a single Home load**, not threads leaked across navigation. So `onDestroy` completeness is worth auditing on its own merits (this item's original scope), but it would not have prevented #728; that needed a bound on *simultaneous* launches, which item (2)'s plugin now enforces structurally. **Runtime half shipped 2026-08-23 ([ADR 0031](../adr/0031-task-thread-ceiling.md)).** The ledger left `#if debug` and now records every launch in all builds; `launchTask()` **refuses** above `TASK_THREAD_WATERMARK = 50` live threads, returning false — the contract an invalid node already had. Measured real peak is **9-11** against Roku's cap of 100 (4-library and 13-library servers both), so it cannot fire in normal use, only when something is fanning out. The PRIMARY defense is a pre-ship device gate ([`task-thread-peak.spec.js`](../../tests/rta/specs/task-thread-peak.spec.js), peak < 30), not the ceiling: a store build strips `roku-log` and excludes `#if debug`, so a refusal has no production channel to report on. Cost measured on the screen rather than computed - **11.56 ms on cold start** (12 launches at 963.6 us; the seven bootstrap launches run on the MAIN thread and pay the rendezvous render-thread launches do not) and **2.86 ms** on an `ItemDetails` open (8 launches at 357 us). **Directions (1) and (3) below remain OPEN** - this closed the runtime-enforcement half of (2), not the floor audit or the `onDestroy` completeness audit. Note: the #744 `SideEffectTask` FIFO conversion is **task-count-neutral** — it stays a single Task; the per-request `ApiResultNode` children are plain Nodes (`extends="Node"`), not Task threads.

#### `no-lint-for-mlog-without-logger`

- **area**: [`scripts/lint/log-manager-init-check.js`](../../scripts/lint/log-manager-init-check.js), [`scripts/bsc-plugins/`](../../scripts/bsc-plugins/), any component codebehind calling `m.log.*`.
- **issue**: A component can call `m.log.warn(...)` while never constructing a Logger, and nothing catches it. `m.log` is then `invalid` and the call faults at runtime with `&hf3` ("Interface not a member of BrightScript Component") — a crash, not a silent no-op. `lint:log-manager-init` validates that the *manager* is stood up (`JRScene.init`), not that each component using `m.log.*` ever ran `m.log = new log.Logger(...)`. Found live in `components/home/HomeRows.bs`, which had a single `m.log.warn` on the latest-rows stall-reclaim path and no Logger anywhere in it or its `JRRowList` ancestor. It had never been seen because that path only fires when a run outlives its own budget; it surfaced immediately once a second `m.log` call was added to a path that runs every time. The failure mode is nasty precisely because it hides on rare branches — exactly the error-handling code you least want to fault.
- **direction**: A BSC plugin in the existing convention-plugin family (same `afterValidateFile` + AST visitor shape as [`no-direct-sdk.cjs`](../../scripts/bsc-plugins/no-direct-sdk.cjs) / [`no-raw-run.cjs`](../../scripts/bsc-plugins/no-raw-run.cjs)): flag any `m.log.<level>(...)` call in a file that contains no `m.log = new log.Logger(...)` assignment. Must account for inheritance — a codebehind may legitimately rely on an ancestor's `init` having set `m.log`, so resolve up the `extends` chain before flagging (both teardown plugins already walk `parentComponent`, so the machinery exists). Sweep first: run it as a warning to size the count before making it an error, since a wide first-run diagnostic count is likely.

  **Second check — argument count.** `Logger.info` is `function(message, value..value9)` — 10 params — and the `roku-log` plugin spends the first slot on the injected pkg path, so a call site may pass at most **nine**. Exceeding it is **not** a compile error (`npm run validate` passes clean); it faults at runtime with `Wrong number of function parameters` (`&hf1`), which drops the app into the BrightScript debugger and **hangs it mid-load**. That hang then presents as broken *tooling* rather than a bad log call — ODC requests time out, every ODC node read returns `undefined` so RTA nav helpers report "screen never loaded", and the UI sits on a spinner — which is what makes it expensive to diagnose.

  **This check does NOT need the new plugin above — it belongs in [`roku-log.cjs`](../../scripts/bsc-plugins/roku-log.cjs) itself.** That plugin already walks every log call (`isCallExpression` + `WalkMode.visitAllRecursive`), already holds `callExpr.args`, and already knows `config.insertPkgPath` — which is the exact +1 that makes the ceiling 9 rather than 10. The diagnostic is a few lines there, and the test harness exists (`transpile-with-plugin.js`, `roku-log.test.js`). Gate at the strictest bound (`> 9`) regardless of the current `insertPkgPath` setting: prod sets it `false`, but the fault surfaces on the dev builds people actually test with. The missing-Logger check above still wants the separate convention-plugin shape, because it needs to resolve up the `extends` chain and `roku-log.cjs` does no inheritance walking.

  **Evidence, and why this is High rather than Medium.** `components/ItemGrid/LoadItemsTask2.bs` shipped a 10-argument call that validated clean and faulted on device, costing most of a session (2026-08-04) before the device console — which names the offending file and line directly — was read. That was not a one-off: it recurs whenever a session adds a lot of logging, across months, and it is a *documented* rule that keeps being broken — which is the case for a gate rather than more prose. See the `.claude`-area followup in [`progress.md`](../progress.md) on auditing documented-but-unenforced rules; the sequencing there is enforcement first, doc tightening second.

#### `rooibos-setup-not-per-test`

- **area**: 22 spec files under [`tests/source/unit/`](../../tests/source/unit/) and [`tests/source/integration/`](../../tests/source/integration/) that build or mutate node state in `setup()`. (`JRListDialog.spec.bs` was converted in passing during the dialog-chrome work, per the fix-them-as-you-touch-them rule in [`tests/CLAUDE.md`](../../tests/CLAUDE.md).)
- **github**: #786 (epic — carries the per-file checklist; sub-issues spin off per group)
- **issue**: rooibos (`6.0.0-alpha.52`) runs `setup()`/`teardown()` **once per suite** and `beforeEach()`/`afterEach()` **once per test** — four distinct hooks on `BaseTestSuite`. 23 suites build their node in `setup()` and then mutate it, so each test inherits whatever the last one left behind; they pass on declaration *order*, not isolation. Confirmed in #781 while adding `Gradient.spec.bs`: a `rotateDegrees = 270` set by one test leaked into the next one *inside the same `@describe`*, which then resolved a different ramp asset and failed — the component was correct, the suite was not isolated. Per-describe grouping does not help. The visible-failure direction is the benign one; the hazard is the inverse — a test that never sets a field it depends on **passes on a neighbor's leftovers**, which is a green assertion of nothing that stays green until someone reorders or deletes that neighbor. It also inverts diagnosis: a leaked field makes a sound component look broken, which cost real time in #781 before the state was instrumented.
- **direction**: Move construction and any mutated state to `beforeEach()` (chaining `super.beforeEach()`), cleanup to `afterEach()`, and leave genuinely immutable per-suite fixtures in `setup()` — the goal is isolation for *mutated* state, not relocating everything. Audit rather than blind-rewrite: a suite where every test sets all the fields it reads is already order-independent. The cheap verification is to reverse the test order in the file and re-run — a suite that only passes in declaration order is the bug. Split by the epic's groupings, one reviewable PR each. Prevention already landed in [`tests/CLAUDE.md`](../../tests/CLAUDE.md), which auto-loads for anyone writing a spec.

#### `home-row-size-recompute-per-row`

- **area**: [`components/home/HomeRows.bs`](../../components/home/HomeRows.bs) — `setRowItemSize()`, and its callers `populateRowFromData` (re-insert branch), `removeRowAtIndex`, `insertLatestMediaSkeletons`, `onLibrariesLoaded`.
- **issue**: `setRowItemSize()` rebuilds three parallel arrays (`rowItemSize`, `rowHeights`, `rowSpacings`) and writes all three to the `RowList`. It ran **once per structural change** — once per row removed because its library returned nothing, once per row re-inserted. Measured on a Streaming Stick 4K it costs **~85 ms a call** early in a load and **~200 ms** once every row is populated, and the removal half fires for every library with no recent items, on every Home load, with `refresh()` running on every return to Home. **Fixed** — removals and their recompute are now batched across a whole latest-rows run, **for the rows that run delivers**. Measured 2026-08-19 on a REAL library set (10 libraries requested, 2 returning nothing), `main` vs the branch, n=30 per arm per tier, alternating blocks, identical `rows=10` workload on every sample, all figures from `measure:compare`: **512 MB 3446 → 2828.5 ms (−17.9%)**, **1 GB 1760 → 1533 ms (−12.9%)**, **2 GB 1162.5 → 1042.5 ms (−10.3%)**, p<0.0001 / p<0.0001 / p=0.0025. The 1 GB pair was replicated with the arm order reversed (−216 ms) after the first campaign's per-block deltas drifted. The win grows as the device weakens because the recompute saving (`other`, ~−105 ms and roughly flat across tiers) drags `wait` down with it — **−308.5 ms on 512 MB against −24.5 ms on the Ultra** — a render thread with less to do stops slowing the Task thread. It also makes the cost **bounded**: `sizeCalls` is 1 on every batched sample and `other` spans 193–222 / 82–112 / 58–73 ms per tier, against main's 202–857 / 93–531 / 76–251. **The scaling with `calls` is also re-derived** (2026-08-19): four path-less libraries were added to the bench server so six eligible libraries returned nothing (14 requested, 6 empty), then deleted again — **`total` 2831.5 → 1648 ms (−41.8%)**, `other` 688.5 → 100 (−85.5%), `wait` 977.5 → 589, `emit` 1391 → 689.5, n=30/arm, **complete separation (U=0) on every column**, `sizeCalls` 1 on every batched sample. So at six structural changes the change is worth roughly 5× what it is worth at two, and the older −36% (n=6/arm at 11 rows) is superseded rather than merely qualified. ⚠️ Six empty libraries is still an **engineered** condition — the bench server has two — so read it as the SCALING result, not as what a real library set gets. ⚠️ A first attempt was discarded because the server's scheduled 12-hourly scans fired mid-campaign and pushed `wait` from ~600 ms to 7–13 s; that presents as the app slowing down, not as server load, so **confirm the server's scheduled tasks are idle before measuring**. What remains is one ~90-200 ms recompute per load, and whether *that* grows with library count is unmeasured — it has only been taken at 11 rows.
- **corrections — three things here did not survive measurement.** Recorded because each is the kind that gets re-proposed from theory. **(1) It is not quadratic in library count.** The per-call price does not grow with row count — 9 calls averaging 87 ms taken at row counts 3..11, against 80 ms a call at 11 rows — so the shape is linear in the number of structural changes. The `184 → 1067 ms` proxy originally cited here is real but confounded: that arm also does per-row `CreateObject` + `insertChild`. **(2) The drain loop is not the batch boundary it looks like.** `onLatestRowsReady` drains a list, but the orchestrator delivers **one row per observer wake** — 11 rows over 11 wakes — so a per-drain flush coalesces nothing. It was built that way first and changed nothing (`other` 957 → 957 ms). **(3) Batching the recompute alone is a visible bug.** The row list shrinks while the arrays still describe the old one, so every row below a removal renders at its neighbor's size — measured through ODC as a square row at portrait height and a wide row at square width, over ~1.0 s of first paint. The removals themselves have to be deferred with it. The permanent `latest-rows size recompute calls <c> drains <d> ms <ms>` line exists so none of this has to be re-derived, and the ODC method that caught (3) is written up in [`home-first-paint-performance.md`](../dev/home-first-paint-performance.md).
- **direction**: **Nothing further to reclaim on this path — measured, not assumed.** Timing the function's own segments (throwaway probe, Stick 4K, 8 runs) shows where the ~90-200 ms actually goes: rebuilding the three arrays costs **0 ms**, writing `rowHeights` **0 ms**, writing `rowSpacings` **0 ms**, and writing **`rowItemSize` is the entire cost** — 114 ms at 13 rows. That is the `RowList` re-measuring every cell against the new slot sizes. It follows the FIELD, not the write order: swapping `rowSpacings` to first still left it at 0 and `rowItemSize` at 112. And it is necessary work rather than waste — a removal genuinely changes the row→slot-size mapping, so a re-layout is owed. The one lever that existed was reducing how *many* times it runs, and batching already took that to 1 per load. Two shapes tried and rejected on measurement, do not re-propose from theory: one `setFields` for the three writes (`total` p=0.24, `other` moved the wrong way), and flushing per drain. **So the "rebuilding three arrays looks inefficient" reading is wrong — the rebuild is free.**
- **why the batch stops at the run's own rows, and the one thing that buys**: `populateRowFromData` serves *every* Home section, so a component-wide batch flag also swallows `resume` / `nextup` / `livetv` / `activeRecordings` removals — which it silently did at first, because the flag was introduced by substituting `rowStructureChanged()` at every existing call site. Two problems with that, and the second is the one that decided it. It is **race-dependent**: those four are fired by `startParallelLoads`, which races the orchestrator, so whether a Continue Watching row collapses immediately or at the end of the run depends on which HTTP response wins — same server, two loads, two behaviors. And it is **unsafe**: the queue is keyed by `sectionId` and held to the end of the run, while `onProgramsExpired` and `Home.refresh()` can both re-fire those tasks mid-run, so a repopulated row could be deleted by a stale queue entry. `latestRows.removalIsDeferrable` is now the seam, and it is unit-tested. What that declines is bounded and small: a recompute only fires for a section that returned **empty**, at most four exist, and two of them only when Live TV is in the server-authoritative plan — so 0 for a user with watch history, ~2 on a fresh account, 4 worst case. Widening the batch to the whole Home load would need a multi-condition close plus a watchdog to buy that back; **not pursued, and the bound above is why**. Re-open only with a measurement, not from the arithmetic.
- **residual, and it belongs to Phase 2 rather than here**: that single write **grows with the row list** — `rowItemSize` cost 62 ms at 5 rows against 114 ms at 13, i.e. roughly **30 ms fixed + ~6.5 ms per row**. ⚠️ **Two data points, and rows and items co-vary across them**, so treat the growth as established and the constant as not pinned. Extrapolating is exactly the error [`home-first-paint-scales-with-library-count`](#home-first-paint-scales-with-library-count) already warns about, so do not quote a 50- or 100-library figure from it. What it does mean: at large library counts this joins the linear-in-rows costs that viewport-lazy hydration is meant to address, and it is one more reason that work is sized against row count rather than item count.

#### `homerows-geometry-invariant-ungated`

- **area**: [`components/home/HomeRows.bs`](../../components/home/HomeRows.bs) (`setRowItemSize`, `applyPendingRowRemovals`, `rowStructureChanged`), [`tests/rta/`](../../tests/rta/)
- **issue**: The row-size batching rests on an invariant no automated check enforces — the three geometry arrays (`rowItemSize` / `rowHeights` / `rowSpacings`) must describe the current row list at all times except inside the batch. Break it and rows below a removal render at their neighbor's size, which is a **visible** defect that produces no error, no log line and no timing change. It has already shipped once and was caught by hand: batching the recompute without deferring the removals drew a square row at portrait height and a wide row at square width for ~1.0 s of first paint. The oracle that caught it — an ODC probe polling `rowItemSize.count()` against the live child count and, where those disagree, each row's own `cursorSize` against the entry actually applied to it — was a throwaway. The unit test added with the batching scope covers *which* removals may defer, not whether the arrays and the tree ever disagree.
- **also unenforced, and it wants the same oracle**: **focus position across the batched drain**. The removals now land as a group at the end of the run rather than one at a time through the load, and `RowList` focus is by *index* — so dropping rows above the focused one shifts what the user is pointed at. Nothing asserts this; the geometry probe and the refresh probe that shipped with the batching both read structure, not focus. - **direction**: Promote that oracle to a standing assertion, covering the geometry invariant and focus preservation together — same probe, same transient, and splitting them would mean building the harness twice. RTA is the natural home — it already drives a real device over ECP + ODC and reads the content tree, which is what this needs; the polling-through-the-transient part matters, since the defect is a window during load rather than an end state. **The second half of the oracle is the load-bearing half**: a length mismatch alone is not a defect (a surplus entry can sit past the last row), so the check has to name which *visible* row is drawn at a size that is not its own. A Rooibos alternative would need a test seam on `HomeRows.xml` to drive a simulated run, which is a bigger interface change than it looks — weigh that against RTA before picking. Method write-up already exists in [`home-first-paint-performance.md`](../dev/home-first-paint-performance.md).
- ⚠️ **Blocked on a fixture we control — do not build this against the public demo server.** The check needs libraries that return no latest items, and `demo.jellyfin.org/stable` yields exactly **one** (`playlists`, 0 latest — measured 2026-08-10; `movies` 8, `music` 4, `tvshows` 1). One deferred removal barely exercises a batch, and the server's metadata is rebuilt hourly, so the moment `playlists` gains an item the assertion passes while verifying nothing — the vacuous-green shape [`tests/rta/CLAUDE.md`](../../tests/rta/CLAUDE.md) already has a rule against. It would also need an `ENABLE_RTA` hold hook in [`LoadLatestRowsTask.bs`](../../components/home/LoadLatestRowsTask.bs) to widen the window deterministically, the way `rtaSkeletonHoldMs` does for the Genres skeleton. This is a **fourth driver** for the decision on a second RTA target (or a local seeded fixture) already captured as an open followup in [`docs/progress.md`](../progress.md) — resolve that first, then this becomes cheap. #### `home-first-paint-scales-with-library-count`

- **area**: [`components/home/HomeRows.bs`](../../components/home/HomeRows.bs) (`populateRowFromData`), [`components/home/LoadLatestRowsTask.bs`](../../components/home/LoadLatestRowsTask.bs).
- **issue**: Even after the #728 batching fix, Home's render-side attach cost is **linear in rows × items** — one `appendChildren` per library row, 16 items each. #### `log-level-welded-to-debug-const`

- **area**: [`components/JRScene.bs`](../../components/JRScene.bs) (`initializeLogManager` call), the `manifest` `bs_const` line, [`scripts/harden-prod-manifest.js`](../../scripts/harden-prod-manifest.js).
- **issue**: The roku-log level is chosen by the `debug` compile-time const — `#if debug` → level 4 (everything), `#else` → level 2 (error/warn/info). So the only way to see `m.log.debug` / `m.log.verbose` output is to edit the `manifest`, flip `debug=true`, and rebuild. Two costs. **(1) You cannot raise verbosity without also changing the app.** `debug=true` attaches `rawApiData` to every transformed item (**+121 ms on a Stick 4K, +178 ms on a 512 MB Stick**, measured), arms failure injection, and enables the toast cheat code — so anything observed while chasing a log line is observed in a distorted build. Open questions for (B): where the value lives (registry setting vs. an in-app dev affordance like the existing up-up-down-down toast chord), whether it survives a restart, and whether it is limited to dev builds. Note `initializeLogManager` cannot move earlier than `JRScene.init` (a platform constraint — see the comment there), so a runtime source must be readable at that point.

#### `per-item-cross-thread-appends`

- **area**: [`components/ItemGrid/BaseGridView.bs`](../../components/ItemGrid/BaseGridView.bs) (`rowsRoot.appendChild` in the genre branch), [`components/home/FavoritesRows.bs`](../../components/home/FavoritesRows.bs), [`components/extras/ExtrasRowList.bs`](../../components/extras/ExtrasRowList.bs), [`components/search/SearchRow.bs`](../../components/search/SearchRow.bs), [`components/liveTv/schedule.bs`](../../components/liveTv/schedule.bs). Fixed already in [`components/home/HomeRows.bs`](../../components/home/HomeRows.bs) — **both** of `populateRowFromData`'s branches.
- **issue**: A loop that appends N nodes one at a time into a row that is **already in the live render tree** is expensive in proportion to N, where one batched call is not. Measured on a Streaming Stick 4K in the Home latest-rows path: **~4.8 ms per item**, 849 ms of a 2646 ms first paint. Replacing the loop with `appendChildren` took that to 328 ms and first paint to 2129 ms (n=10/arm, complete separation, p=0.0002).
  **The mechanism is NOT established, and the earlier wording here overstated it.** This entry previously said the cost was "a rendezvous per `appendChild`" arising from thread ownership. Treat that as unproven: the appending code runs on the render thread, and rendezvous is a cost paid *from the Task side* — see [`threading.md`](threading.md) ("Task nodes are owned by the Render thread, so their fields rendezvous from the Task side"), and `rokudev/dev-doc` v2.0 `DEVELOPER/core-concepts/threads.md` upstream. Two things are measured and safe to rely on — the cost scales with the number of append **calls**, and it only appears when the **target is live in the render tree** (see direction). Don't re-derive a mechanism from the ownership model without new evidence.
- **direction**: For each site, establish whether the node being appended INTO is already attached to the rendered scene graph. Where it is, replace the loop with a single `appendChildren(array)`; where the target is still detached (built, then attached afterwards — the `ConfigList.setData` shape), there is likely nothing to win, so measure before changing. **Measure per site rather than sweeping** — the genre path carries ~8–23 appends against Home's 176, so it may not clear the ~120 ms resolution floor of the first-paint method. Note `LoadItemsTask2.bs:462` (a Task thread appending into its own not-yet-delivered node) is not a candidate on either reading. The `attach`/`detach`/`other` split now permanent in `HomeRows` is the instrumentation template. **Any claimed win must be checked against the live node counts**, because a run that renders fewer items looks identical in the timings: read the content tree off the device on both arms over ECP (the same `getChildCount()` / per-child field reads `tests/rta/` uses — row count, per-row tile count, and tile order) and require them to match exactly before believing a number. **What separates an expensive append from a free one is whether the target is LIVE in the render tree.** Measured on the same device and session by forcing every latest row down the re-insert branch (skeleton insertion disabled, so `detach = 0` proves the path was taken): the identical `appendChildren` of the same items costs **~315 ms into a live row and ~0 ms into a still-detached one** (n=8 vs n=6). The items really do arrive — verified on screen, since an empty run would also report ~0. **This does not make "build detached" a fix**: that same arm ran *slower* end to end (total 2083 → 3266 ms), with `other` absorbing +884 ms. Where the work actually goes, and why, is not established — that arm also does per-row `CreateObject` / `insertChild` / `setRowItemSize` the in-place path never does, and this experiment cannot separate the two. The actionable part needs neither answer: **`attach` alone can mislead**, because a site appending into a detached node reports ~0 whether or not it is optimal. Decide on `total`, not on the column. Surfaced in the #728 Home batching work.

#### `rta-odc-connect-unbounded`

- **area**: [`tests/rta/lib/driver.js`](../../tests/rta/lib/driver.js) (`withTimeout`, `deployRtaBuild`) and every entry point that makes an ODC call before one — [`scripts/rta-run.js`](../../scripts/rta-run.js), [`scripts/capture-screenshots.js`](../../scripts/capture-screenshots.js), [`tests/rta/demos/run.mjs`](../../tests/rta/demos/run.mjs), [`scripts/rta-restore.js`](../../scripts/rta-restore.js).
- **issue**: An ODC call against a device that is not running the on-device component can hang FOREVER, and it presents as a network problem rather than a missing build. RTA's own timeout does not cover it, and this is the part worth writing down because the obvious fix is wrong: `sendRequest` races the request against `getTimeOut(options)` (10 s default), but it `await`s `setupClientSocket()` **before** that race, and that promise only self-rejects on `ECONNREFUSED` / `EPIPE`. A connect to port 9000 that neither connects nor errors leaves it unsettled, and `clientSocketPromise` is cached, so it stays wedged. **Passing a `timeout` option to `readRegistry` / `getValues` therefore does nothing for this case** — the bound has to be an outer wall clock. Read out of `client/dist/OnDeviceComponent.js` on 2026-08-16 rather than inferred. The cost is measured, twice: 39 and 9 minutes on a wedged deploy (#817), and ~10 minutes to diagnose the sign-in case, each initially misread as the network.
- **a SECOND failure mode, measured 2026-08-17: the bounded call does not own its own failure.** The entry above is about the call that never settles. This is the opposite end and it bites the caller who did everything right. `setupClientSocket` RETRIES `ECONNREFUSED`/`EPIPE` once a second and rejects the cached promise only when RTA's own connect timeout expires (`OnDeviceComponent.js:989-1000`). A caller must bound it more tightly than that — which is exactly what `withTimeout` is for — so it handles ITS rejection and moves on while the real promise is still pending. When that one finally rejects there is nobody attached, and it surfaces as an **`unhandledRejection` from a socket error EVENT**, outside every `await` chain, at a point in the run unrelated to the call. Cost: the ODC calibration's two plain-arm blocks each passed their "is the ODC absent?" probe, printed their assertions, then died mid-series with `Failed to connect to Roku ... on port 9000` — recorded `crashed`, no record written. So `withTimeout` alone is NOT sufficient for a caller that expects the call to fail; it converts a hang into a delayed crash.
- **direction**: Two of the four paths are guarded — `deployRtaBuild` via `DEPLOY_TIMEOUT_MS`, and `measure-signin.js` via `SIGNIN_TIMEOUT_MS` — both now built on the exported `withTimeout(promise, ms, message)`. The remaining exposure is every entry point whose FIRST ODC call happens outside those two: `rta-run.js`'s `snapshotRegistry()` under `RTA_NO_DEPLOY=1`, `rta-restore.js`, the screenshot orchestrator and the demo runner. The cheap version is wrapping each first ODC call in `withTimeout` with a message naming the cause; the thorough version bounds `setupClientSocket` once inside `lib/driver.js` so no caller has to remember. Prefer the latter if it can be done without forking RTA — the per-caller version is a rule that will be forgotten by the fifth entry point. Whatever the shape, the message must name the likely cause (resident build has no ODC — a Rooibos test build or a `build:prod` both present this way) rather than the elapsed seconds. **A third option now exists and is cheaper than both for the ASK-FIRST case:** [`odcIsResident(host)`](../../scripts/measurement-guard.js) is a raw TCP probe of port 9000 that resolves `true`/`false` in one round trip, never rejects, and touches none of RTA's client — so an entry point can gate on it before the first real ODC call instead of bounding that call. It answers "is anything listening", not "is the component healthy"; that is the right strength for a precondition check and the wrong one for a liveness check. Note the fix must ALSO cover the second failure mode above — a permanent no-op `.catch()` on the cached promise is the only thing that stops a late rejection being unhandled once someone has given up waiting on it.

#### `measure-record-assembly-untested`

- **area**: [`scripts/measure.js`](../../scripts/measure.js) — everything from the `Close the boundary` marker to the end of the file (~370 lines): the `record` object appended to `measurements.jsonl`, the pure statistics (`medianOf`, the per-timing-key medians, `lineCoverage`), and the console presentation.

#### `dialog-channels-unarbitrated`

- **area**: [`source/utils/dialogs.bs`](../../source/utils/dialogs.bs), [`components/dialogs/JRKeyboardDialog.bs`](../../components/dialogs/JRKeyboardDialog.bs), [`components/video/VideoPlayerView.bs`](../../components/video/VideoPlayerView.bs)

#### `playback-error-dialog-closed-by-teardown`

- **area**: [`components/video/VideoPlayerView.bs`](../../components/video/VideoPlayerView.bs), [`components/video/PlayerHostView.bs`](../../components/video/PlayerHostView.bs)
- **issue**: The player's own error dialog can be dismissed by code before the user reads it, and dismissing it fires a navigation into the middle of another one. `showPlaybackErrorDialog` puts a raw Roku `Dialog` on the MODAL channel and observes `wasClosed` → `onPlaybackErrorDialogClosed` → `exitPlayback()`, so *closing it navigates*. The buffering-stall path then opens it and immediately stops the stream: `showPlaybackErrorDialog(...)` followed by `m.top.control = "stop"` ([`VideoPlayerView.bs` `bufferCheck`](../../components/video/VideoPlayerView.bs)). A `stop` can surface as state `finished` — recorded in `PlayerHostView.onPlayerStateChange`'s own comment about the DoVi fallback — and that handler's only guard is `m.view.isRetrying`, which is written solely by `retryPlayback` and so is false here. It reaches `cancelOpenDialog()`, which closes the modal channel, which fires the error dialog's close handler and calls `exitPlayback()`. `onPlayerStateChange` then carries on and either advances the queue or calls `exitPlayback()` a second time. Net: the error message is never read, and a `goBack()` races a queue advance.
- **severity**: Low. **Pre-existing and NOT introduced by the #288 phase-3 migration** — the deleted `SceneManager.dismissDialog` did the identical `m.scene.dialog.close = true` behind the identical `isDialogOpen()` gate, so behavior is unchanged across that branch. Reachability of the stall path itself is unmeasured; it needs a stream that stalls mid-buffer, which the demo fixture does not reliably produce.
- **direction**: The bug is a close handler doing double duty — `wasClosed` cannot tell a user dismissal from a programmatic one, so it navigates for both. Give the dialog an explicit dismissal path (track whether teardown closed it, or drive the exit from the button rather than from `wasClosed`) so a close driven by code rather than the user is inert. Consider also whether the stall path should show a dialog it is about to stop out from under: opening a message and calling `stop` on the next line is the sequence that makes this reachable at all. Do NOT "fix" it by making `cancelOpenDialog()` skip the modal channel — the OSD and end-of-playback teardown genuinely need the screen clear, and a stranded modal is the failure that gate exists to prevent.

#### `trackdropdown-selected-treatment`

- **area**: [`components/ui/dropdown/TrackDropdownRow.bs`](../../components/ui/dropdown/TrackDropdownRow.bs)
- **github**: #288 (dialog standardization — surfaces with the rest of the picker work)
- **issue**: `TrackDropdownRow` marks the CURRENT track by rendering its label in `colorTextSecondary`, which plays the user's existing pick *down* rather than marking it. The two other components answering the same question disagree with it and with each other: `JRDropdownItem` recolors the selected label to `colorSecondary` (and only while unfocused), while `JRListDialogRow` marks the row with a `colorSecondary` check glyph over a `colorBackgroundSecondary` surface and leaves the label at `colorTextPrimary`. ## Recently removed — don't go searching for these

- **`matrix-cannot-establish-its-own-precondition`** (tech-debt slug: `npm run measure:devices` could ASSERT that every device sat on one Jellyfin server but not ESTABLISH it, so a cross-tier run meant signing three devices in by hand before every run — and because the sanctioned workflow restores each one afterwards, that ritual recurred indefinitely) — **resolved 2026-08-16 by `npm run measure:devices -- --sign-in <url> --user <name>`**, which per device seeds an authenticated session, measures, and restores. Built to the entry's own direction: the seed lives on the DRIVER only ([`measure-signin.js`](../../scripts/measure-signin.js), one child per device for the `roku-test-automation` singleton reason), single-device `measure` still never writes the registry, and the lifecycle is the existing one — `snapshotRegistry()` before any write, `seedHome`, `assertSeedTookEffect`, `npm run rta:restore` afterwards. Both named traps were carried over rather than rediscovered (`hardRelaunch()` first; per-device `DeviceId`s from the `ROKU_IP` hash), and `seedServerSelect` was avoided as instructed. **One deliberate deviation from the recorded direction**: it restores PER DEVICE rather than once at the end of the matrix, which falls out of the per-device child structure and is strictly safer — a device is put back whether its measurement passed, failed, or never ran. Rules that could be made pure are (`parseSignIn`, `signalPolicy` in [`measure-matrix.js`](../../scripts/measure-matrix.js)); `--sign-in <url>` implies `--server <url>` so tier 1 still hard-asserts what was actually seeded, and a repeated or contradicting server flag is a refusal rather than a silent last-one-wins. Verified on three RAM tiers with an identical `--nav settings` workload at n=5: 512 MB `3600X` 73/430 ms, 1 GB `3820RW` 58/296 ms, 2 GB `4850X` 25/135 ms, all three `VERIFIED CLEAN`; the 1 GB reading was checked against that device's hand-established n=30 baseline of 57/297.5 ms to show the seeded session does not perturb what it measures. One residual was filed rather than folded in, [`rta-odc-connect-unbounded`](#rta-odc-connect-unbounded). A second — `measure.js` not releasing its device lock on a SIGNAL — was filed and then FIXED in the same branch instead, because this mode promoted it from theoretical to routine: the driver kills the in-flight `measure` child on a first interrupt, so interrupting a matrix stranded a lock every time, and the next run lost a whole RAM tier to a lock held by a dead process id before anyone typed the entry. `measure.js` now mirrors `rta-run.js`'s `SIGINT`/`SIGTERM`/`SIGHUP` handlers, folding the run as `interrupted` rather than letting the exit net call an operator's deliberate stop a crash.

- **`measure-single-device-only`** (tech-debt slug: `npm run measure` drove exactly one device from `ROKU_IP`, so a cross-tier matrix meant re-exporting it per device by hand) — **resolved 2026-08-16 by [`npm run measure:devices`](../../scripts/measure-devices.js)**, which reads an optional `ROKU_DEVICES=<ip>,<ip>,<ip>` from `.env` and runs the same measurement on each in turn, `ROKU_IP` still the single-device default. The entry's own split held: `.env` declares which devices EXIST, [`roku-hardware.json`](../../scripts/data/roku-hardware.json) declares what tier a model IS, so a contributor lists only addresses and gets tier labels free — this is the first production caller of `describeDevice` / `cannotRunApps`. The confound the entry was filed over (two devices on the demo server beside one on a real server, reading as a hardware difference until the `rows` column was checked) is now a **hard refusal**: a matrix run must pass `--server <url>` or `--no-server`, because the server is the workload and only the multi-device layer knows there is more than one arm. It reproduced on this tool's very first run, which is why it became a gate rather than a third warning. Devices run sequentially (`--deploy` wipes `build/`; the server is shared; the ledger is append-only), out of process because `roku-test-automation` binds its client singletons to one host per process. Verified on three RAM tiers at n=5 with an identical 10-row workload: 512 MB `3600X` 3271 ms, 1 GB `3820RW` 1805 ms, 2 GB `4850X` 1202 ms.
