Either upload it, or narrow the claim in `device-lock.js`'s header to local-only and stop implying CI benefits. (The header now says local-only; the artifact-upload option is still unexercised.)
- Expand automated store screenshots from the 5 marketing languages to ALL ~99 locale files, to surface the default Roku OS font's blast radius — boxes/tofu for scripts the system font doesn't cover are EXPECTED and the point of capturing them. From #642.
- **`.device-runs/` has no operator-facing verb, and it now holds a secret at rest indefinitely.** The registry snapshot (`.device-runs/registry-<host>.json`) is the device's WHOLE registry including `authToken` for the active server. Moving it out of `out/` fixed a real recovery bug, but it also removed the incidental cleanup a `npm run build` used to perform — so nothing deletes it now except a verified restore or `npm run rta:restore`, and the case that strands it is precisely a restore that never converged (the `authToken` re-mint that caused this is fixed — see [`restore-compares-credentials-by-presence`](decisions.md) — but any residual has the same shape). The ledger `.device-runs/<kind>/runs.jsonl` is likewise append-only with nothing pruning it. **Evidence, 2026-08-11 (friction event, not speculation):** during review of this branch a stranded snapshot on `.177` was destroyed by an `rm -rf .device-runs` issued against a misread path, and recovery needed hand-writing `JellyRock.active_user` + `server` back over ODC — there was no tooling for either half, and no way after the fact to know what the directory had held. The ledger history from the 2026-08-10/11 verification runs was lost with it. That is the friction: the recovery state has no verb, so operating on it means knowing which gitignored path to delete and which registry keys to hand-write. **Fix shape:** extend [`scripts/device-lock.js`](../scripts/device-lock.js) (which already owns `status` / `release`) with a `clean` subcommand that prunes ledgers and refuses to touch a snapshot without an explicit flag plus a warning naming the device it would strand; and add a `device:status` line reporting whether a snapshot is currently stranded — that alone would have surfaced this before anything was deleted.

Raised in review of #806 and deliberately not folded in — the RTA side is what Phase 3 reads, and the device ledger has one line in it today.

They will drift, and the half worth sharing is the **replay-window handling**: a socket that connects and sits completely idle receives a stale `latest-rows run complete` line **10 ms later** reading `7241 ms`, against a live range of 1439–2654 ms that same session (measured on `.177`, 2026-08-12). `measure.js` defends against that twice — one socket held for the whole session, plus per-sample timestamp selection — while the Rooibos runner reconnects per invocation and has no equivalent (it reads `[Rooibos Result]` markers, so a replayed marker would report a stale verdict; whether that can actually happen is unverified and is the first thing to check). **Fix shape:** extract the tail into a shared reader and migrate `run-roku-tests.js` onto it. - **`npm run measure`'s ODC-precondition refusal has never run against real hardware.** The tool refuses before taking a sample when ODC does not answer (the device is not holding an RTA-deployed build) or when the app answers with no `serverUrl` (not signed in). - **Does a resident ODC component move a first-paint number? The instrument's own calibration, and it is BLOCKED BY CONSTRUCTION today.** `npm run measure` reads identity over ODC and refuses without it, and ODC exists only in an `ENABLE_RTA` build — so the `ENABLE_RTA=false` arm of the experiment cannot be taken by the tool at all, and `npm run measure:compare` now explicitly refuses to compare arms that differ in `enableRta`. **What is and is not at risk:** a delta between two `measure` arms is unaffected (both arms are RTA builds, so a constant offset cancels), and so is a device-matrix comparison; what is affected is the ABSOLUTE number, and any comparison against the n=30 baselines in [`home-first-paint-performance.md`](dev/home-first-paint-performance.md), which were taken in non-RTA builds. That cross-comparison is the one concrete harm and it is already closed — the refusal is in code rather than in prose. **Three steps, in order, and the first two are prerequisites:** (1) extract `measure.js`'s sampling loop (console window, replay defense, quiet-break) into a module a calibration harness can drive — it lives in the entry point today, so a harness would otherwise duplicate it; (2) decide what an arm without ODC may claim about its identity, which needs an ADR because carrying it from the paired RTA build across a redeploy is INFERRED rather than observed, and that is the one rule the measurement guard exists to enforce; (3) run it interleaved on all three RAM tiers, not just `.177` — a resident task plausibly costs most on the 512 MB Stick, so a one-device answer would be the least informative version. Deliberately deferred out of rta-reliability at its close (2026-08-13): the calibration is not on the critical path for the perf PR deltas it exists to serve, and doing it properly needs a refactor plus an ADR rather than a mode bolted onto a tool that was just verified on hardware.

- **The search keystroke race is DETECTED, explained, and unreachable in practice — nothing acts on it, by choice.** Two shapes were argued from reading `SearchResults` when the readiness ledger landed: a `contentReady` mark delivered after the next keystroke opened a new run (→ the `unbalanced` warning), and a `results` delivery answering a superseded query (→ a short number filed against the wrong query, plus a torn-down observer so the live query's results never arrive). **Neither reproduced, and the second now has a mechanism rather than a shrug.** Probed on `.177` 2026-08-14 over ECP at two keystroke intervals straddling the measured ~570 ms query (8 at 1400 ms, 12 at 550 ms): zero `unbalanced` lines, every published run settled with 2 fills, and — with launch/delivery logging — **12 launches produced 6 deliveries, all 6 answering the current query.** `SearchTask.searchMedia` assigns `m.top.results` exactly once as its last statement, so each keystroke's `control = "stop"` lands before the publish and a superseded query does not deliver at all; the remaining exposure is one field-write wide. Two further unknowns were settled in the same run: Scene Graph does **not** suppress a content-equal `assocarray` write (a repeat identical query re-delivered and re-settled with `alwaysNotify` removed, so no such attribute is needed on `results`/`itemData`), and the per-keystroke `observeField("results", ...)` re-registration produced **no** duplicate `loadResults` invocation across 12 registrations. **So the branch instruments rather than intervenes:** the query echo plus a log line in `loadResults` assert the invariant without acting on it, and `onResultRowsReady` and the `focus` resolve are left unguarded because `resolve` already refuses to count a fill that was never pending and its warning is the only signal that would show the race is real. **What would reopen this:** anything that makes the search publish incremental or earlier results, or a much slower library that widens the notification window. A `superseded search delivery` line, or `screen-load unbalanced` naming `rows`, is the first real observation — fix it then, on that evidence.
